# CI/CD 도입 설계

> 작성일: 2026-07-29
> 대상 환경: Oracle Cloud VM.Standard.E2.1.Micro (AMD x86, 1 OCPU / RAM 1GB), Spring Boot 3.4 + Kotlin, Gradle, GitHub 저장소
> 프론트엔드는 Vercel이 자동 배포 중 — 본 문서는 백엔드만 다룸

## 0. 한 문장 요약

> **push하면 GitHub이 빌려주는 컴퓨터에서 빌드와 테스트를 돌리고, 통과한 jar만 서버로 보내서, 서버의 스크립트가 교체·재시작하고, 앱이 안 뜨면 이전 버전으로 자동 복귀**

- **CI** (Continuous Integration) = push할 때마다 빌드+테스트를 자동으로 돌려서 깨진 코드를 걸러내는 것
- **CD** (Continuous Deployment) = 검증을 통과한 결과물을 자동으로 서버에 반영하는 것

## 1. 왜 CI/CD가 필요한가

지금 배포 방식: 서버 SSH 접속 → `git pull` → `./gradlew clean build` → 재시작. 문제는 "귀찮다"가 아니라 다음 세 가지.

**① 1GB 서버에서 빌드하고 있음 — 이게 제일 큰 문제**

빌드하는 동안 서버에는 운영 중인 앱(JVM) 위에 Gradle과 Kotlin 컴파일러가 추가로 뜸. 즉 **배포할 때마다 메모리가 가장 부족한 순간을 우리 손으로 만들고 있는 셈**. 운이 나쁘면 빌드가 죽는 게 아니라 운영 중인 앱이 메모리 부족으로 강제 종료(OOM kill)될 수 있음. 앞으로 Redis까지 들어오면 여유는 더 줄어듦.

CI를 도입하면 빌드는 GitHub이 빌려주는 컴퓨터(러너, RAM 7GB)에서 하고 서버는 **실행만** 담당. 이것이 이 설계의 첫 번째 동기.

**② 테스트 없이도 배포가 됨**

지금은 테스트를 안 돌리고도 배포 가능. CI가 있으면 push마다 빌드+테스트가 강제로 돌아서, 컴파일 안 되는 코드나 기존 기능을 깨는 변경이 서버에 도달하기 전에 걸러짐. "배포 전에 확인했나?"가 사람의 기억력이 아니라 자동 검증이 됨.

**③ 배포 절차가 머릿속에만 있음**

수동 배포는 순서 하나만 빼먹어도(환경변수 누락, 재시작 잊음) 장애로 이어짐. 그리고 배포가 잘못됐을 때 되돌리는 방법이 `git checkout` 후 **재빌드**뿐이라, 롤백에도 빌드 시간이 통째로 소요. 파이프라인으로 만들면 절차가 코드로 남아 매번 똑같이 실행되고, 롤백은 보관해 둔 직전 jar로 즉시 가능.

부수 효과: 배포가 자동이면 작은 변경을 자주 배포하게 됨. 변경 단위가 작을수록 문제가 생겼을 때 원인 범위도 작음.

## 2. 도구 선택 — 왜 GitHub Actions인가

CI/CD 도구의 양대산맥은 Jenkins와 GitHub Actions. 결정적 차이는 하나:

> **Jenkins는 "CI 서버를 내가 직접 운영"하는 것, GitHub Actions는 "GitHub이 운영해주는 것"**

| 관점 | Jenkins | GitHub Actions |
|---|---|---|
| 실행 환경 | 내 서버에 설치하고 직접 관리 | GitHub이 제공, 관리할 것 없음 |
| GitHub 연동 | 웹훅·자격증명 수동 설정 | 기본 내장 (PR 화면에 결과 표시) |
| 비용 | 서버 리소스 + 관리 시간 | public 저장소 무제한 무료 |
| 파이프라인 정의 | Jenkinsfile | YAML 파일 (레포 안에 커밋) |

Jenkins를 선택하지 않는 이유:

1. **서버가 하나 더 생기는 셈** — Jenkins는 그 자체가 관리해야 할 서버 애플리케이션. 설치, 플러그인, 보안 패치를 전부 직접 해야 함. 우리의 유일한 VM(1GB)에 올리면 운영 앱과 메모리를 나눠 써야 하는데, Jenkins 최소 권장 메모리부터가 1GB라 애초에 불가능
2. **해커의 단골 타깃** — Jenkins를 쓰려면 웹 화면을 인터넷에 노출해야 하는데, Jenkins는 전 세계에서 가장 많이 공격 시도되는 대상 중 하나. 운영 서버와 같은 VM에 있으면 Jenkins가 뚫리는 순간 서비스 전체가 뚫림
3. **Jenkins가 필요한 상황이 하나도 해당 안 됨** — Jenkins가 맞는 회사는 폐쇄망이라 외부 서비스를 못 쓰거나, GitHub이 아닌 자체 Git 서버를 쓰거나, 빌드가 너무 많아 자체 장비가 더 싼 경우. 셋 다 이 프로젝트와 무관. **도구의 우열 문제가 아니라 제약 조건의 문제이고, 우리 제약 조건에서는 GitHub Actions가 정답**

Railway, Render 같은 PaaS(push만 하면 알아서 배포해주는 유료 서비스)는 무료 티어를 포기해야 하고, 배포 과정이 블랙박스라 배우는 게 없어서 제외.

## 3. 왜 Docker를 안 쓰는가

실무 표준은 Docker 이미지로 배포하는 것이지만, 여기서는 **jar 파일을 직접 전송**. 몰라서가 아니라 따져보고 뺀 것.

1. **메모리가 아까움** — Docker는 컨테이너를 안 돌리고 있어도 데몬(dockerd + containerd)이 상시 수십~100MB를 점유. Redis한테도 64MB만 허락한 1GB 서버에서, "배포를 편하게 해주는 도구"가 Redis보다 메모리를 더 먹는 건 앞뒤가 안 맞음. [redis-design.md](redis-design.md)에서 Redis를 apt로 설치하기로 한 것과 같은 판단
2. **Docker의 장점이 여기선 발휘될 데가 없음** — Docker의 가치는 "어느 환경에든 똑같이 배포"(이식성), 여러 컨테이너 격리, 오케스트레이션에서 나옴. 배포 대상이 **VM 1대, 프로세스 1개**면 이 장점이 하나도 해당 안 됨. 게다가 jar는 이미 "JVM만 있으면 어디서든 도는" 파일이라 이식성 문제의 절반은 애초에 없음
3. **환경이 달라서 생기는 문제는 다른 방법으로 방지** — Gradle 설정이 Java 21을 고정(toolchain)하고 있어서, CI에서 빌드한 jar와 서버가 실행하는 jar의 Java 버전이 어긋날 일 없음
4. **컨테이너로 얻으려던 운영 기능은 systemd에 이미 있음** — 부팅 시 자동 시작, 죽으면 자동 재시작, 로그 관리. 리눅스 기본 기능으로 충분

단, **서버를 스케일업하면 Docker 전환을 재검토**. RAM 4GB+ 환경이면 메모리 반론이 사라지고 이식성 가치가 생김. 그때도 이 문서의 CI 부분(빌드+테스트)은 그대로 재사용 가능.

## 4. 파이프라인 설계

### 4.1 전체 흐름

master에 push하면 GitHub이 러너(임시 컴퓨터)를 한 대 띄워서 순서대로 진행:

```
[PR 생성/갱신]
  └─ CI만 실행: 빌드 + 테스트          ← 머지해도 되는지 검사하는 관문

[master push]
  ① 러너가 코드를 받아 ./gradlew build 실행 (테스트 포함)
       └─ 실패하면 여기서 끝. 서버는 건드리지도 않음
  ② 성공하면 jar가 나옴
  ③ 러너가 jar를 서버로 전송 (SCP = SSH로 파일 복사)
  ④ 러너가 서버에 SSH 접속해 deploy.sh 실행을 지시하고 빠짐
```

GitHub Actions가 하는 일은 이게 전부: **빌드하고, 파일 보내고, 스크립트 하나 실행.** 실제 교체 작업은 서버의 `deploy.sh`가 담당 (4.3).

### 4.2 워크플로 파일

`.github/workflows/deploy.yml` 파일 하나에 build job과 deploy job을 두고 `needs:`로 연결. build가 성공해야만 deploy가 실행되는 구조. PR에서는 build job만 돌도록 조건 처리.

```yaml
# 핵심 구조 (요약)
on:
  pull_request:          # PR에서는 빌드+테스트만
  push:
    branches: [master]   # master push면 배포까지

concurrency:
  group: deploy
  cancel-in-progress: false   # 배포 중에 또 push해도 중단 없이 순서대로

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4              # 코드 받기
      - uses: actions/setup-java@v4            # Java 21 설치
      - uses: gradle/actions/setup-gradle@v4   # 의존성 캐싱 → 빌드 수 분이 수십 초로
      - run: ./gradlew build                   # 테스트 포함
      - uses: actions/upload-artifact@v4       # jar를 다음 job에 넘기기

  deploy:
    needs: build         # build 성공이 조건
    if: master push일 때만
    steps:
      - uses: actions/download-artifact@v4
      - # jar SCP 전송 → SSH로 deploy.sh 실행
```

### 4.3 deploy.sh — 서버에서 일어나는 일

지금 손으로 하던 재시작 과정을 스크립트로 적어둔 것. 개념만 보면:

```bash
mv app.jar app-prev.jar          # ① 돌고 있던 jar를 "직전 버전"으로 보관 (보험)
mv app-new.jar app.jar           # ② 방금 받은 새 jar를 현역으로
systemctl restart atleti-news    # ③ 재시작
curl localhost:8080/api/...      # ④ 앱이 살아났는지 확인 (헬스체크, 최대 60초 재시도)
# ④ 실패 시: app-prev.jar를 되돌리고 재시작 → 자동 롤백
```

**왜 이 로직을 워크플로 YAML에 안 넣고 서버에 두나** — 서버에 스크립트로 있으면 GitHub Actions가 고장 난 비상 상황에도 서버 접속해서 `./deploy.sh`만 치면 똑같이 배포됨. 자동 배포와 비상 수동 배포가 같은 코드를 쓰게 되는 것. `deploy.sh`도 레포에 커밋해서 버전 관리.

**헬스체크란** — 거창한 게 아니라 "재시작한 앱에 API 하나 호출해보고 200이 오는지 확인". 새 코드에 문제가 있어 앱이 아예 안 뜨면, 사람이 알아채기 전에 스크립트가 먼저 알고 이전 버전으로 복원. 별도 라이브러리(Actuator) 추가 없이 기존 공개 API로 판정 — 1GB 환경에서 의존성 하나도 아끼는 취지.

**다운타임에 대하여** — 재시작하는 수십 초 동안 서비스가 잠깐 끊김. 이를 없애려면(무중단 배포) 앱 2개를 띄워놓고 번갈아 교체해야 하는데, 1GB에서 JVM 2개는 불가능. 뉴스 서비스 특성상 수십 초 단절은 수용 가능하다고 **판단하고 명시적으로 유예** — 몰라서 안 한 게 아니라 따져보고 안 한 것임을 기록해 두는 것.

### 4.4 서버 측 구성

```
/opt/atleti-news/
 ├─ app.jar        # 현재 버전 (systemd가 실행하는 대상)
 ├─ app-prev.jar   # 직전 버전 (롤백용)
 ├─ app-new.jar    # 전송 직후 임시 이름
 ├─ deploy.sh      # 배포 스크립트
 └─ .env           # 환경변수 (레포에 없음, 서버에서만 관리)
```

- systemd 유닛 `atleti-news.service`: `ExecStart=java -jar /opt/atleti-news/app.jar`, 죽으면 자동 재시작(`Restart=on-failure`), JVM 힙 상한 명시(`-Xmx400m` 수준 — 1GB 예산 안에서 운용)
- 배포 유저에게 sudo 전체가 아니라 **`systemctl restart atleti-news` 딱 하나만** 비밀번호 없이 허용(sudoers). 배포용 SSH 키가 유출돼도 할 수 있는 게 "앱 재시작"뿐이도록 피해 범위 축소
- 전환 후 서버의 git 체크아웃은 배포 경로에서 빠지므로 제거 가능

### 4.5 테스트 실행 조건

현재 테스트는 `AtletiNewsApplicationTests`(앱이 뜨는지 확인) 하나. CI 러너에는 PostgreSQL도 API 키도 없으므로, **h2 프로파일로 실행**하고 필수 환경변수는 워크플로에서 더미 값 주입. CI가 생기면 앞으로 작성하는 모든 테스트가 자동으로 머지 관문에 편입되는 것도 부수 효과.

## 5. 시크릿(비밀값) 관리

풀어야 할 문제는 하나: **러너가 우리 서버에 SSH 접속하려면 열쇠(SSH 키)가 필요한데, 열쇠를 코드에 적어둘 수는 없음.**

해결책은 **GitHub Secrets** — 레포 설정에 있는 금고. 값을 넣어두면 워크플로에서 `${{ secrets.OCI_SSH_KEY }}`처럼 이름으로만 꺼내 쓰고, 코드에 안 남고, 로그에 찍혀도 자동으로 `***` 마스킹.

| 시크릿 | 저장 위치 | 용도 |
|---|---|---|
| `OCI_HOST` | GitHub Secrets | 서버 IP |
| `OCI_USER` | GitHub Secrets | SSH 접속 계정 |
| `OCI_SSH_KEY` | GitHub Secrets | 배포 전용으로 새로 만든 SSH 개인 키 |
| DB 비밀번호, Gemini API 키 등 | 서버 `.env` | **파이프라인에 안 태움** (아래) |

**앱의 비밀값(DB 비밀번호 등)은 왜 GitHub Secrets에 안 넣나** — 파이프라인의 일은 "jar 전달"이지, 앱이 무슨 비밀번호를 쓰는지 알 필요 없음. 비밀값은 존재하는 장소가 적을수록 안전하므로 지금처럼 서버 `.env` 한 곳에서만 관리.

**방화벽 참고** — SSH(22번 포트)를 개인 IP에만 열어뒀다면 러너가 접속 불가. 러너의 IP는 매번 바뀌므로, 현실적으로는 22번을 열되 키 인증 전용 + fail2ban(반복 침입 시도 자동 차단)으로 방어. 추후 Tailscale 같은 VPN으로 좁히는 것은 선택 과제.

## 6. 구현 로드맵

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | CI 워크플로 (build job) 작성 | PR에서 빌드+테스트 자동 실행, 실패 시 머지 차단 표시 |
| 2 | 서버 준비: 배포 디렉터리, systemd 유닛, 배포 유저/키, sudoers | **`deploy.sh`를 손으로 실행해서** 정상 기동 확인 |
| 3 | deploy job 연결 (SCP 전송 + `deploy.sh` 호출) | master push → 서버에 자동 반영 |
| 4 | 자동 롤백 검증 | **일부러 깨진 jar를 배포**해서 이전 버전으로 자동 복원되는지 확인 |
| 5 | (선택) Discord/Slack 배포 알림, README 뱃지 | 배포 결과 알림 수신 |

순서에 이유가 있음:

- **2단계에서 손으로 먼저 돌려보는 이유** — 한 번에 다 연결하고 실패하면 스크립트 문제인지 GitHub 연동 문제인지 구분 불가. 손으로 검증해 두면 이후 실패는 무조건 연동 쪽으로 좁혀짐. 디버깅 범위를 반으로 자르는 순서
- **4단계에서 일부러 고장 내보는 이유** — 롤백이 진짜 장애 때 처음 작동하게 두면 안 됨. 미리 한 번 고장 내고 되돌아오는 걸 눈으로 확인해 두는 것

## 7. 결정 사항 요약 (Q&A 대비)

- **왜 GitHub Actions인가** — CI 서버를 직접 운영하면 유일한 1GB VM에서 운영 서버와 같이 죽고, 공격 표면도 늘어남. Jenkins가 맞는 조건(폐쇄망, 자체 Git, 대규모 자체 러너)은 해당 사항 없음. 도구의 우열이 아니라 제약 조건의 문제
- **왜 Docker 없이 jar 직배포인가** — 1GB에서 도커 데몬 상시 오버헤드(~100MB)를 감당할 이유가 없고, VM 1대·프로세스 1개에는 Docker의 이식성·격리 가치가 발휘 안 됨. 서버 스케일업 시 전환 재검토
- **왜 빌드를 서버가 아닌 러너에서 하나** — 현재는 서버에서 `git pull` + 빌드 중이라 운영 앱과 빌드가 1GB 메모리를 경쟁. 러너(7GB)에서 빌드하고 산출물만 보내면 서버는 실행만 담당
- **왜 무중단 배포가 아닌가** — JVM 2개를 동시에 띄워야 하는데 1GB에서 불가능. 뉴스 서비스 특성상 수십 초 단절은 수용. 스케일업 시점의 과제로 명시적 유예
- **롤백 전략은** — 직전 jar 1개 보관 + 헬스체크 실패 시 자동 복원. 단순하지만 단일 인스턴스 규모에는 충분하고, "배포 실패가 서비스 중단으로 이어지지 않는다"는 요구를 만족
- **앱 시크릿은 왜 파이프라인에 안 태우나** — 파이프라인은 jar 전달만 하면 되고 앱의 비밀값을 알 필요 없음. 사본이 존재하는 장소는 적을수록 안전하므로 서버 `.env` 한 곳만 유지
