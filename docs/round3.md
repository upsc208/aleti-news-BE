## 이 경기의 산수

증상 넷이 같은 식 하나로 떨어진다.

```
화면 체감 지연 = 소스 도착 지연 + (설정 지연 D − 중계 지연 L)
```

`D = 25초`(`LIVE_DELAY_SEC` 기본값)이고, 시계는 소스 도착 지연이 0이다 — 기준점이
"시각 값"이라 늦게 받아도 값 자체는 안 밀리기 때문이다. 그래서 ②의 9초가 곧 `D − L`이고,
여기서 **이 경기의 중계 지연 `L ≈ 16초`**가 나온다. 나머지는 그 위에 얹힌 소스 도착 지연이다.

| 증상 | 체감 지연 | ⇒ 소스 도착 지연 | 무엇이 늦었나 |
|---|---|---|---|
| ② 시계 | 9초 | 0초 | — (설계상 값) |
| ① 보드 점등 | 40초 | **31초** | `firstHalfStarted` 확보 |
| ④ 골 | 20초 | **11초** | 네이버 골 반영 |
| ⑤ 승리 | 60초 | **51초** | 네이버 `경기종료` 라벨 |

> **전제 두 가지.** ㉮ 서버 `.env`의 `LIVE_DELAY_SEC`가 기본값 25초라고 봤다. 다르면 위
> 역산이 통째로 바뀐다. ㉯ FE 시계는 기기의 `Date.now()`를 그대로 쓴다 — 측정에 쓴 폰
> 시계가 어긋나 있으면 모든 숫자가 그만큼 밀린다(서버 시각 기준 보정은 아직 없다).

## ① 보드가 40초 뒤에 켜졌다

25초는 설계값이다. 시청자가 아직 킥오프를 못 봤으니 보드도 꺼져 있는 게 맞다.
문제는 나머지 **31초 — 시계 기준점을 그만큼 늦게 받았다.**

`firstHalfStarted`가 있으면 그 시각이 오기 전까지 `formatMatchClock`은 `null`을 돌려주고
보드는 후원 화면(`pre`)으로 남는다. 그 기준점은 FotMob에서만 오는데, 기준점이 없는 구간의
조회 간격이 15초(`CLOCK_URGENT_RETRY`)라 여기서 평균 7.5초, 거기에 FotMob 자체 반영 시간이 붙는다.

킥오프 직후 구간만 5초로 좁히면 15초쯤 당길 수 있다. 그러면 시청자 기준 25초 — 설계값에 붙는다.

## ③ 하프타임에 시계가 안 멈췄다 — 후반 시작이 **12초 만에** 찍혔다

서버 로그(`journalctl -u atleti-news`, 8/29 19:00~22:30 UTC)로 확정했다. 짐작했던 두 갈래
(네이버 표기 불일치 / FotMob 폴백)는 **둘 다 아니었다.** 원인은 문서 아래에 "덧"으로 달아 뒀던
반대 방향의 위험이었다.

로그의 `periods`는 `delayed()`를 통과한 값이라 25초를 뺀 실제 시각으로 적는다.

| 서버 시각(UTC) | 무슨 일 |
|---|---|
| 19:30:43 | 전반 시작 (`firstHalfStarted`, FotMob) |
| 20:21:51 | **전반 종료 — FotMob이 알려줬다** (`firstHalfEnded`) |
| 20:22:03 | ⚠️ **후반 시작이 찍혔다** — 전반 종료 **12초** 뒤 |
| 20:22:33 | 네이버가 그제서야 `전반종료`로 바뀜 (전반 종료로부터 42초) |
| 20:38:34 | 진짜 후반 시작. FotMob 값이 잘못된 값을 덮어썼다 |

화면은 20:22:28(=찍힌 값 + 지연)부터 후반으로 알고 **45:00부터 다시 셌다.** 하프타임 16분
43초 동안 시계가 계속 돌아 61:31까지 갔고, 진짜 값이 도착하자 45:00으로 되돌아갔다 —
관측된 "안 멈추고 돌다가 후반에 45분으로 돌아갔다"가 정확히 이것이다.

### 왜 12초 만에 찍혔나 — 두 소스가 같은 순간을 다른 시각에 안다

```kotlin
// 문제의 조건
if (!snapshot.halftime && !snapshot.finished &&
    anchor.firstHalfEnded != null && anchor.secondHalfStarted == null) { ... }
```

"하프타임이 **아니면** 후반"이라고 봤다. 이 조건은 `firstHalfEnded`도 네이버가 준다는 전제
위에서만 맞다 — 그때는 두 값이 같은 응답에서 나오니 어긋날 수가 없다.

그런데 이번엔 **FotMob이 전반 종료를 42초 먼저 알려줬다.** 그 42초 동안 네이버는 아직
`전반 50'`이었고, 그건 하프타임 표기가 아니므로 조건이 그대로 참이 됐다.

### 이번에 알아낸 표기 — 라리가는 분 단위다

로그에 남은 이 경기의 `statusInfo` 전체다.

```
전반 1' → 전반 3' → … → 전반 50' → 전반종료 → 후반 1' → … → 후반 51' → 경기종료
```

**`경기중`은 한 번도 안 나왔다.** 설계 문서와 코드 주석이 예로 들던 값인데 실제 라리가
표기는 분 단위였다. 라운드 1이 "다음 경기 로그에 남게 해 두자"고 한 **하프타임의
`statusCode`도 여기서 확인됐다 — `STARTED`다**(종료 코드가 아니다).

### 고친 것

후반은 **소스가 후반이라고 말할 때만** 찍는다(`isSecondHalf`). `전반 50'`도 `전반종료`도
후반이 아니다. 모르는 표기는 규정 휴식 15분이 지난 뒤에야 후반으로 본다 — 표기가 대회마다
다르므로 뒷문을 아예 막으면 모르는 대회에서 시계가 하프타임에 갇힌다.

`후반종료`처럼 **`종료`를 품은 표기는 부분 일치로 걷어낸다.** 종료 판정에서 부분 일치를
금지한 라운드 1과 반대로 보이지만 묻는 질문이 다르다 — 저쪽은 잘못 참이면 경기가 통째로
날아가고, 이쪽은 잘못 참이면 **경기 끝에 시계가 45:00으로 되돌아간다.**

> **폴백 구멍은 없던 문제였다.** 갈래 2로 의심했던 "FotMob 폴백 중에는 백업 경로가 없다"는
> 사실이지만, 폴백은 곧 **네이버가 죽었다는 뜻**이라 애초에 메꿀 재료가 없다. 그 상태에서는
> FotMob의 `halfs`가 유일한 시계이고, 그게 안 오면 방법이 없다. 고칠 것이 아니다.

## ④ 골이 20초 늦다 — 지연이 두 번 얹힌다

라운드 2에서 넣은 "늦게 온 골은 더 붙잡지 않는다"(`releaseAnchor`)가 **이번 경기에서는
사실상 안 걸렸다.**

```kotlin
holdFrom = min(도착 시각, 골이 일어난 시각)   // 골 시각 = 그 분의 가장 늦은 순간
```

발생 시각을 **분의 끝**으로 잡기 때문에 추정치가 도착보다 뒤인 경우가 대부분이고, 그러면
`min`이 늘 도착 시각을 고른다. 결국 골은 `도착 + 25초`, 시계는 `실제 + 25초` — **골만 소스
도착 지연(11초)만큼 더 늦는다.** 8/23처럼 네이버가 51초 늦게 준 골에서는 이 장치가 제대로
먹지만, 소스가 빠른 경기에서는 아무 일도 하지 않는다.

**여기서 `LIVE_DELAY_SEC`를 낮추는 것은 답이 아니다.** 20초로 낮추면 이번 경기 골은 15초 뒤로
붙지만, 8/20처럼 중계가 33초 느린 경기에서는 골 알림이 시청자보다 **2초 앞서** 스포일러가 된다.
25초는 사실상 하한이다.

## ⑤ 승리 효과 1분 뒤

`25초(설정 지연) + 51초(네이버 경기종료 라벨 지연) − 16초(중계 지연)`이다. FE는
`FINAL_STATUS` 정확 일치로만 축포를 띄우는데(라운드 1에서 `전반종료`가 `종료`로 읽혔던 사고
때문에 정확 일치로 바꿨다), 그 상태 자체가 네이버에서 51초쯤 늦게 온다.

후반에는 교체 때문에 어차피 20초마다 FotMob을 부르고 있으므로, **종료는 두 소스 중 먼저 아는
쪽을 쓰면** 추가 비용 없이 줄일 수 있다. 얼마나 줄지는 FotMob `status.finished`의 반영 속도에
달렸고, 그건 아직 안 재봤다.

## 로그 보는 법

**서버는 UTC다.** `--since`를 KST로 쓰면 엉뚱한 구간을 뒤진다 — 04:30 KST 경기는 전날
19:30 UTC다. journal은 영구 보존(`/var/log/journal`)이라 7/29치까지 남아 있다.

```
ssh -i ~/.ssh/atleti-deploy-key ubuntu@168.110.106.79 \
  "journalctl -u atleti-news --since '2026-08-29 19:00' --until '2026-08-29 22:30' --no-pager | grep -a '\[Live\]' | head -100"
```

구간을 안 자르면 저널 전체(수십 MB)가 흘러나온다. `--since/--until`을 반드시 붙인다.

### 남은 확인 항목

**㉮ 서버 `.env`의 `LIVE_DELAY_SEC` 실제 값.** 위 역산 전체가 25초라는 전제 위에 서 있다.
로그의 `periods`와 실제 시각의 차이가 정확히 25초였으니 맞을 것이나, 확인은 아직이다.

**㉯ FotMob 라이브 응답의 `Cache-Control`.** 라운드 2에서 넘어온 미확인 항목이다.

## 고친 것 (2026-08-31)

### ① 기준점을 못 받은 구간의 조회 간격 15초 → 5초

`clockRetryInterval`이 "기준점이 **하나도** 없다"를 이제 따로 본다. 킥오프 직후에는 폴링
턴마다(5초) FotMob에 묻고, **예정 킥오프 +10분**(`KICKOFF_CLOCK_WATCH`)이 지나면 15초로
물러선다 — 매핑이 어긋나 `halfs`를 영영 못 받는 경기에서 243KB를 세 시간 내내 받지 않기
위한 상한이다. 세레머니로 킥오프가 8분 20초 늦었던 8/20도 이 창 안에 들어온다.

기대: 보드 점등이 평균 7.5초, 최악 15초 당겨진다. **나머지는 FotMob 몫이라 우리가 못 줄인다** —
라이브 응답 캐시가 5초보다 길면 그만큼은 그대로 남는다(아직 실측 전).

### ③ 후반 시작은 소스가 후반이라고 **말할 때만**

`isSecondHalf`를 새로 두고, "하프타임이 아니다"로 후반을 판정하던 조건을 갈아 끼웠다.
`전반 50'`도 `전반종료`도 후반이 아니다. 판정 근거는 세 갈래다.

| 소스 표기 | 판정 |
|---|---|
| `후반 N'` · `경기중` | 후반 — 그 자리에서 찍는다 |
| `전반 N'` · `전반종료` · `경기종료` · `*종료` | 후반 아님 — 안 찍는다 |
| 모르는 표기 | 규정 휴식 15분이 지난 뒤에야 후반으로 본다 |

세 번째 줄이 뒷문이다. 표기가 대회마다 다르므로(라리가가 `경기중`을 안 쓴다는 걸 이번에
알았다) 아예 막으면 모르는 대회에서 시계가 하프타임에 갇힌다. 15분이면 실측 휴식(16분 43초·
16분 53초)보다 짧아 늦지 않고, 이번 같은 12초 오작동과는 거리가 멀다.

이 경기를 다시 태우면: 20:22:03에는 `전반 50'`이라 안 찍고, 그다음은 `전반종료`라 안 찍고,
20:38:34에 FotMob의 진짜 값이 들어온다. **시계는 51:08에서 멈췄다가 45:00으로 간다.**

### ⑤ 종료는 두 소스 중 먼저 아는 쪽

후반에는 교체 때문에 어차피 [SUBS_RETRY](20초)마다 FotMob을 부른다. 그 응답의 `finished`를
같이 보고 네이버보다 먼저면 그 턴부터 종료로 내보낸다 — **호출 수는 그대로다.** 화면이 상태
문구 정확 일치로 축포를 띄우므로 플래그만이 아니라 표기(`경기종료`)까지 바꾼다.

일찍 잡는 실수를 막는 조건 둘:

- **후반 시작 +40분(=85분)이 지나야 인정한다.** 정규 시간이 5분 넘게 남았는데 끝났다는
  응답은 무시한다 — 8/20에 종료를 일찍 잡아 후반이 통째로 날아갔다
- **기준점이 없으면 인정하지 않는다.** 대볼 시계가 없으면 지금까지처럼 네이버를 기다린다

한 번 잡으면 유지한다(`finishedEarly`). 네이버는 그동안 아직 `후반 51'`이라, 매 턴 다시 물으면
보드가 종료됐다 되살아난다 — 축포는 이미 터진 뒤라 되돌릴 수도 없다.

기대: 네이버 51초 → FotMob 반영 속도 + 조회 간격(최대 20초). **얼마나 줄지는 다음 경기에
재봐야 한다.** FotMob이 종료를 얼마나 빨리 찍는지는 아직 모른다. 로그에 이 줄이 남는다.

```
🏁 [Live] 종료를 FotMob이 먼저 알려줬습니다 — 네이버는 아직 '후반 51''
```

이 줄이 **안** 보이면 네이버가 더 빨랐다는 뜻이고, 그것대로 알아낸 값이다.
