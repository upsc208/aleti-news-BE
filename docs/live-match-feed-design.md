# 라이브 경기 정보 피드 설계

> 작성일: 2026-08-10
> 대상 환경: Oracle Cloud VM.Standard.E2.1.Micro (1 OCPU / RAM 1GB), Spring Boot 3.4 + Kotlin, Redis 7.x
> 관련 문서: [redis-design.md](redis-design.md)
> 측정 도구: [`scripts/measure-live-feed.js`](../scripts/measure-live-feed.js)

## 1. 목표와 범위

킥오프 시각에 열리는 매치 채팅방에 **현재 스코어와 득점자 이름**을 실시간으로 밀어준다.

한 줄 요약: **네이버 스포츠 내부 API를 5초마다 서버 하나가 대신 조회하고, 바뀐 것만 기존 채팅 WebSocket으로 밀어준다.**

비유하자면 **Redis는 물탱크다.** 관을 굵게 하는 일(=지연 단축)은 데이터 소스 선택이 이미 해결했고, Redis는 200명이 동시에 수도를 틀어도 본관은 초당 0.2번만 열리게 막아주는 역할이다.

### 1.1 하는 것

| 항목 | 비고 |
|---|---|
| 현재 스코어 | 홈/원정 득점 |
| 득점자 이름 | **한글**, 시간(분) + 추가시간, 자책골 여부 |
| 골 발생 시 채팅방 알림 | 기존 `chat.messages` Pub/Sub 재사용 |
| VAR 취소 시 정정 알림 | 골 목록에서 사라진 항목 감지 |

### 1.2 하지 않는 것 (의도적으로 제외)

필요한 정보가 스코어와 득점자뿐이므로, 아래는 **범위 밖**으로 명시해 둔다.

- 카드·교체·점유율·xG·슈팅 등 상세 지표 → 경기 종료 후 기존 FotMob 파이프라인이 이미 처리 중
- 문자중계(코멘터리), 하이라이트 영상, 라인업 실시간 변동
- 골 이력의 영구 보관 → 채팅과 동일하게 휘발성으로 다룸
- 유료 데이터 계약 → 4장 참고, 현 단계에서 불필요하다고 판단
- **스포일러 방지용 지연 버퍼** → 4.2 실측 결과에 따라 불필요. 단서는 9장 참고

## 2. 데이터 소스 결정: 네이버 스포츠

### 2.1 결론

**라이브(채팅 푸시)는 네이버, 경기 종료 후 상세는 기존 FotMob 유지**하는 하이브리드로 간다.

### 2.2 실측 비교

2026-08-10 직접 호출해 확인한 값이다.

| 항목 | **네이버** | FotMob |
|---|---|---|
| 엔드포인트 | `api-gw.sports.naver.com/schedule/games/{gameId}` | `www.fotmob.com/api/data/matchDetails?matchId=` |
| 인증 | `Referer: https://m.sports.naver.com/` 만 필요 | 불필요 |
| 캐시 헤더 | `no-cache, no-store, must-revalidate` | `max-age=10` (CloudFront) |
| 응답 크기 | **2.6KB** | 251KB (gzip 28KB) |
| 선수 이름 | **한글** ("아르나우 오르티스") | 영문 ("Iván Martin") |
| 자책골 | `ownGoal` | `ownGoal` |
| 추가시간 | `addedTime` | 없음 |

### 2.3 네이버를 고르는 이유

우선순위 순이다.

1. **한글 선수 이름** — 한국어 채팅방에서 "이반 마르틴 골!"이 "Iván Martin"보다 낫다. FotMob을 쓰면 별도 음역 테이블을 만들고 계속 관리해야 하는데, 네이버는 그 작업이 통째로 사라진다.
2. **응답이 100배 작다** — 2.6KB 대 251KB. 1GB VM에서 경기 내내 도는 작업이라 파싱 비용 차이가 그대로 부하 차이가 된다.
3. **캐시가 없다** — FotMob은 CDN이 10초 TTL로 막고 있어 그보다 짧게 폴링해도 같은 캐시본만 돌아온다. 네이버는 매 요청이 원본에 닿는다.
4. **무료.**

> 3번은 처음에 1순위 근거였다. 폴링을 2초까지 줄일 계획이었기 때문인데, 4장의 실측으로 그럴 필요가 없어지면서 중요도가 내려갔다. 결론은 1·2번만으로도 유지된다.

### 2.4 FotMob을 남겨두는 이유

xG·라인업·카드·교체는 이미 `MatchScraperService`가 처리하고 있고 잘 동작한다. 경기 종료 후 한 번 긁는 용도라 캐시 TTL도 문제가 되지 않는다. **굳이 옮길 이유가 없다.**

> 참고: FotMob의 구 경로 `/api/matchDetails`는 현재 404이고 `/api/data/matchDetails`로 이동했다. 스크래핑 경로가 깨지면 이 지점을 먼저 확인할 것.

## 3. 네이버 API 스펙 (실측)

### 3.1 경기 상세

```
GET https://api-gw.sports.naver.com/schedule/games/{gameId}
Referer: https://m.sports.naver.com/
```

응답에서 우리가 쓰는 필드:

```json
{
  "result": {
    "game": {
      "gameId": "QyRcDHa8DA07hWz",
      "gameDateTime": "2026-08-15T00:30:00",
      "categoryName": "클럽 프렌들리",
      "stadium": "스타드 벨로드롬",
      "homeTeamName": "마르세유",  "homeTeamScore": 0,
      "awayTeamName": "AT 마드리드", "awayTeamScore": 1,
      "statusCode": "RESULT",
      "statusInfo": "경기종료",
      "scorers": {
        "home": [],
        "away": [ { "time": 43, "addedTime": 0, "playerName": "호르헤 도밍게스", "ownGoal": false } ]
      }
    }
  }
}
```

### 3.2 일정 조회 (gameId 확보용)

```
GET https://api-gw.sports.naver.com/schedule/calendar
      ?upperCategoryId=wfootball&categoryId=primera&yearMonth=2026-08
```

날짜별 `gameIds` 배열을 돌려준다. 여기서 얻은 id로 3.1을 호출해 아틀레티 경기를 찾는다.

### 3.3 알아둘 표기·엔드포인트 특성

- **라리가 = `categoryId: "primera"`**
- **아틀레티코 마드리드 = `"AT 마드리드"`** (`"아틀레티코"`로 검색하면 안 잡힌다)
- `schedule/games?...` 목록 엔드포인트는 파라미터 조합을 못 찾아 **400**만 반환. `schedule/calendar`로 우회한다.
- `/record`, `/preview`, `/relay` 하위 경로는 200이지만 내용이 비어 있고, `/relation`은 403.

### 3.4 확인된 아틀레티 일정

`node scripts/measure-live-feed.js --find` 로 언제든 다시 뽑을 수 있다.

| 일시(KST) | 대회 | 경기 | gameId |
|---|---|---|---|
| 08-15 00:30 | 클럽 프렌들리 | 마르세유 vs AT 마드리드 | `QyRcDHa8DA07hWz` |
| 08-20 04:00 | **라리가** | AT 마드리드 vs 말라가 | `Z5BQDTTiMjv6iBO` |
| 08-24 00:00 | 라리가 | AT 마드리드 vs 비야레알 | `nSpr6NeOefWQhYU` |
| 08-30 04:30 | 라리가 | 세비야 vs AT 마드리드 | `PqXMiW4TGD8Y0KW` |

> "리야드 에어 메트로폴리타노"는 아틀레티코 홈구장(마드리드 메트로폴리타노)의 스폰서 변경 명칭이다. 데이터 이상이 아니다.

## 4. 지연 분석

### 4.1 물리적 한계

골이 채팅에 뜨기까지의 경로:

```
실제 골 →[2~10초]→ 현장 스카우트 입력 →[제공사 반영]→ 네이버 API →[폴링 0~5초]→ 서버 →[~1ms]→ 유저
          ↑ 전체 지연의 대부분                                        ↑ 우리가 줄일 수 있는 유일한 구간
```

- **"골 발생 2초 이내"는 어떤 계약으로도 불가능하다.** Sportradar가 12,600명의 현장 수집원을 두고 말하는 "sub-second"는 스카우트가 버튼을 누른 **이후**의 배포 지연이다. 사람이 보고 누르는 2~10초는 돈으로 줄일 수 없다.
- 네이버·구글도 같은 한계 위에 있다. 둘은 Opta(Stats Perform)·Sportradar급 엔터프라이즈 라이선스 피드를 연 단위로 계약해 push로 받지만, 물리적 바닥은 동일하다.

| 소스 | 갱신 주기 | 가격 | 방식 |
|---|---|---|---|
| **네이버 (채택)** | 캐시 없음 → 폴링 주기가 곧 지연 | 무료(비공식) | 폴링 |
| FotMob | ~10초 (CDN TTL) | 무료(비공식) | 폴링 |
| API-Football (api-sports/RapidAPI) | 15초 | 무료~$29/월 | 폴링 |
| Sportmonks | ~15초 | €29/월~ | 폴링 |
| Goalserve Livescore | 3~5초 | $150/월 | 폴링 |
| Entity Sport Gold | sub-second | $150~400/월 | WebSocket |
| Sportfast.io | ms 단위 | $999+/월 (WS는 Enterprise만) | WebSocket |

RapidAPI 마켓플레이스의 축구 API 대부분은 위 소스들을 재판매하는 래퍼라 **원본보다 빨라질 수 없다.** 유료 전환의 실익이 없다고 판단한다.

### 4.2 시청 환경 실측 — 쿠팡플레이

유저 다수가 쿠팡플레이로 경기를 틀어놓고 채팅에 참여한다. 봇이 시청자보다 빠르면 **실시간 정보가 아니라 스포일러**가 되므로, 이 격차가 설계의 핵심 변수다.

**실측 (2026-08-09, 맨시티 vs AT 마드리드, 서울월드컵경기장):**
경기장에서 실제 경기를 보며 휴대폰으로 쿠팡플레이를 동시에 재생해 비교. **지연 약 5초.**

일반적인 HLS 기반 OTT가 20~45초인 것에 비해 매우 빠르다. LL-HLS(저지연 HLS)를 쓰면 4~8초가 가능하므로 기술적으로 타당한 수치다.

**결론: 지연 버퍼는 만들지 않는다.**

```
0초     ⚽ 실제 골
+5초    🖥️ 쿠팡플레이 화면에 골 장면
+10~15초 📱 네이버 반영 → 봇 감지 → 채팅방 알림
```

봇이 오히려 시청자보다 **5~10초 느리다.** 스포일러가 되지 않으므로 지연 기능 자체가 불필요하다.

### 4.3 이 수치의 한계 — 재측정이 필요한 이유

위 5초는 **국내 제작 중계**에서 나온 값이다. 라리가는 중계 경로가 더 길다.

```
어제 (서울월드컵경기장)  : 현장 제작 → 인코딩 → CDN                       ← 짧음
라리가 (마드리드/세비야) : 스페인 제작 → 국제 전송 → 한국 수신
                         → 재인코딩 + 한국어 해설 → CDN                  ← 단계가 더 많음
```

같은 쿠팡플레이여도 해외 피드를 수입하는 라리가 중계는 더 느릴 수 있다. **8/20 말라가전이 라리가 경로를 처음 확인할 수 있는 경기**이므로, 그때 9장의 절차로 재측정한다.

## 5. 설계

### 5.1 구조

```
[LiveMatchPoller]  ── 방이 열린 경기당 1개, 5초 주기
   │
   ├─ ① Redis 리더 락 획득 (실패하면 이번 턴 스킵)
   ├─ ② 네이버 API 호출 (2.6KB)
   ├─ ③ live:state:{matchId} 에 스냅샷 저장       ← 입장자 조회용
   ├─ ④ live:goals:{matchId} 와 비교
   │      · 새로 생긴 골  → GOAL 발행
   │      · 사라진 골     → GOAL_CANCELLED 발행
   ▼
Redis PUBLISH chat.messages ──▶ ChatMessageRelay (기존 코드, 수정 불필요)
                                     └─▶ /topic/chat/{matchId}
```

**브로드캐스트 경로는 새로 만들지 않는다.** `ChatMessageRelay`가 이미 `chat.messages`를 구독하고 있으므로, 골 이벤트를 `ChatMessage`로 감싸 같은 채널에 발행하면 방 전체에 그대로 밀린다.

### 5.2 Redis 키 (redis-design.md 4장 표에 추가)

| 키 패턴 | 타입 | TTL | 용도 |
|---|---|---|---|
| `live:poll:{matchId}` | String (`SET NX EX`) | 10s | 폴러 리더 락 |
| `live:state:{matchId}` | String (JSON) | 6h | 현재 스코어 + 득점자 스냅샷 |
| `live:goals:{matchId}` | Set | 6h | 발행 완료한 골 키 |
| `live:map:{matchId}` | String | **24h** | FotMob matchId → 네이버 gameId |
| `live:map:miss:{matchId}` | String | 30m | 매핑 실패 표식 (구현 중 추가) |
| `live:end:{matchId}` | String | 6h | 경기 종료를 처음 감지한 시각 (구현 중 추가) |
| `live:src:{matchId}` | String | 6h | `live:goals`의 키를 만든 소스 (구현 중 추가, 8.6) |

메모리는 **방 1개당 약 2KB.** `maxmemory 64mb` 상한에 영향 없다.

> 구현하며 조정한 것 세 가지:
> - `live:map` **6h → 24h.** 매핑은 19:00 배치에서 만들어지는데 킥오프가 다음날 04:00이면
>   6h TTL은 정작 킥오프 전에 만료된다.
> - `live:map:miss` 추가. 짝을 못 찾은 경기에 이게 없으면 **5초마다** 월간 캘린더 전체를
>   다시 훑는다(경기 상세 수십 건). 실패를 30분 기억하는 쪽이 훨씬 싸다.
> - `live:end` 추가. "종료 +10분에 멈춘다"(5.4)를 재시작·다중 인스턴스에서도 지키려면
>   종료 감지 시각이 인스턴스 메모리가 아니라 Redis에 있어야 한다.
>
> 리더 락은 TTL(10s)이 주기(5s)보다 길어 **자기 락을 이어 잡는 처리**가 필요하다.
> 없으면 리더가 자기 락에 막혀 매 두 번째 턴을 통째로 건너뛴다.

### 5.3 각 키가 필요한 이유

**`live:poll` — 폴러가 둘 이상 도는 것을 막는다.**
현재 `FootballDataService.claimRefreshSlot()`은 `AtomicReference`로 중복 갱신을 막는데, 이는 **JVM 하나 안에서만** 유효하다. 배포 중 인스턴스가 겹치거나 서버를 늘리면 그대로 깨져 네이버에 두 배로 요청이 나간다. Redis 락으로 올리면 이 문제가 사라진다.

**`live:state` — API 호출을 접속자 수와 분리한다.**
입장 시점에 라이브 스코어를 내려줄 때 매번 네이버를 호출하면, 하프타임에 200명이 새로고침하는 순간 200번 호출이 된다. 폴러만 쓰고 입장자는 Redis에서 읽게 하면 **네이버 호출이 방당 5초에 1회로 고정**된다. `chat:msg` List로 최근 메시지를 주는 기존 패턴과 같은 구조다.

**`live:goals` — 중복 알림 방지 + VAR 취소 감지.**
네이버 `scorers`에는 FotMob의 `eventId` 같은 고유 키가 **없다.** 다음과 같이 합성해 `SADD` 반환값이 1일 때만 발행한다.

```
{H|A}|{time}+{addedTime}|{playerName}|{ownGoal}
예) A|43+0|호르헤 도밍게스|false
```

- 이것이 없으면 **앱 재시작 시 이미 알린 골을 전부 다시 알린다.** 매치데이 중 배포 한 번이면 채팅방이 골 알림으로 도배된다.
- 또한 VAR 취소는 "골 목록에서 항목이 사라지는" 형태로 나타나므로, 직전 상태를 들고 있지 않으면 **감지 자체가 불가능하다.** 사라진 키를 찾아 정정 메시지를 발행하고 `SREM`한다.

### 5.4 폴링 정책

| 항목 | 값 | 근거 |
|---|---|---|
| 주기 | **5초** | 4.2에서 봇이 이미 시청자보다 느림. 더 줄여도 체감 이득이 없고 부하만 늘어남 |
| 구간 | 킥오프 ~ 경기 종료 + 10분 | 방 오픈(킥오프 −1h)보다 좁게. 3시간 내내 돌리면 낭비 |
| 킥오프 전 | 방 오픈부터 **60초** 주기 (구현 중 추가) | 이게 없으면 킥오프 전 입장자에게 내려줄 스냅샷이 없어 6.2의 "경기 전이면 `경기전` 0-0으로 내려준다"를 지킬 수 없다. 시간당 60회면 충분 |
| 동시성 | 경기당 폴러 1개 | 접속자 수와 무관 |
| 실패 시 | 지수 백오프, 429면 즉시 주기 완화 | 캐시가 없어 원본을 직접 때리므로 예의가 필요 |
| 스코어 표시 | append가 아니라 **현재 상태 덮어쓰기** | VAR로 점수가 되돌아갈 수 있음 |

경기당 요청량은 약 2,160회(3시간 기준)다. 2초 주기 대비 60% 적다. `User-Agent`와 `Referer`를 정상값으로 유지한다.

## 6. API 계약

**설계 원칙: 골 메시지에 스코어 스냅샷을 같이 싣는다.** 프론트는 스코어보드를 위해 별도 요청을 하지 않는다. 골 메시지 하나가 「채팅 라인 추가」와 「스코어보드 갱신」을 동시에 처리한다.

### 6.1 DTO 변경

```kotlin
enum class ChatMessageType { USER, GOAL, GOAL_CANCELLED }

data class ChatMessage(
    val matchId: String = "",
    val nickname: String = "",
    val content: String = "",
    val sentAt: OffsetDateTime? = null,
    val ipHash: String? = null,
    val type: ChatMessageType = ChatMessageType.USER,  // 추가
    val live: LiveMatchState? = null                   // 추가 (GOAL 계열에만)
)

data class LiveMatchState(
    val status: String, val homeTeam: String, val awayTeam: String,
    val homeScore: Int, val awayScore: Int,
    val scorers: List<LiveScorer>, val updatedAt: OffsetDateTime
)

data class LiveScorer(
    val name: String, val time: Int, val addedTime: Int,
    val isHome: Boolean, val ownGoal: Boolean
)
```

`type` 기본값이 `USER`라 기존 것이 깨지지 않는다. Redis List(`chat:msg:*`)에 이미 쌓인 JSON에 `type` 필드가 없어도 역직렬화되고, 클라이언트가 보내는 `{nickname, content}`도 그대로 유효하다.

### 6.2 입장 시 — `GET /api/chat/{matchId}`

기존 `ChatRoomResponse`에 `live` 한 필드만 추가한다.

```json
{
  "open": true,
  "onlineCount": 143,
  "messages": [ ],
  "live": {
    "status": "경기중",
    "homeTeam": "마르세유",
    "awayTeam": "AT 마드리드",
    "homeScore": 0,
    "awayScore": 1,
    "scorers": [
      { "name": "호르헤 도밍게스", "time": 43, "addedTime": 0, "isHome": false, "ownGoal": false }
    ],
    "updatedAt": "2026-08-15T01:14:22+09:00"
  }
}
```

`live`는 **nullable** — 자유 채팅방(`free`)이거나 gameId 매핑에 실패하면 `null`. 경기 전이면 `status: "경기전"`에 0-0으로 내려줘서 킥오프 전에도 스코어보드를 그릴 수 있게 한다.

### 6.3 골 발생 시 — WebSocket `/topic/chat/{matchId}`

```json
{
  "matchId": "4821337",
  "type": "GOAL",
  "nickname": "매치봇",
  "content": "⚽ 43' 호르헤 도밍게스",
  "sentAt": "2026-08-15T01:14:25+09:00",
  "ipHash": null,

}
```

### 6.4 VAR 취소 시

```json

  "type": "GOAL_CANCELLED",
  "nickname": "매치봇",
  "content": "⚠️ VAR 판독 — 43' 호르헤 도밍게스의 골이 취소되었습니다",
  "sentAt": "2026-08-15T01:16:03+09:00",
  "live": { }

```

### 6.5 상태만 바뀐 시각 — 킥오프·하프타임·후반 시작·종료 (8/15 이후 추가)

```json
{
  "matchId": "4821337",
  "type": "STATUS",
  "nickname": "매치봇",
  "content": "",
  "sentAt": "2026-08-15T01:18:22+09:00",
  "ipHash": null,
  "live": { }
}
```

**본문이 비어 있고 `live`만 나른다.** 채팅 라인으로 그리지 않고 스코어보드·시계만 갱신한다.

이게 없던 동안 `live`를 나르는 통로는 골 알림뿐이었다. 그래서 **골이 없는 구간에서는
스코어보드가 통째로 멈췄다** — 8/15 마르세유전에서 드러난 문제가 정확히 이것이다 (10.2).

`chat:msg` 목록에는 **저장하지 않는다.** 대화가 아니므로 늦게 들어온 사람의 내역에
빈 줄로 남으면 안 된다. 놓쳐도 다음 상태 변화나 골에서 다시 실려 나가고,
입장 시 6.2가 어차피 최신 스냅샷을 준다.

발행 조건은 `status` 또는 `periods`가 직전 스냅샷과 달라진 턴 하나뿐이다.
**점수는 조건에 없다** — 점수가 바뀌는 순간은 곧 골이고 그건 6.3이 이미 나른다.

### 6.6 일반 유저 메시지 — 기존과 동일

```json
{
  "matchId": "4821337",
  "type": "USER",
  "nickname": "골레아도르",
  "content": "골이다!!!",
  "sentAt": "2026-08-15T01:14:31+09:00",
  "ipHash": "a3f9"
}
```

### 6.7 프론트 처리

```js
// 입장
const room = await fetch(`/api/chat/${matchId}`).then(r => r.json());
if (room.live) renderScoreboard(room.live);
room.messages.forEach(renderMessage);

// 실시간
stomp.subscribe(`/topic/chat/${matchId}`, frame => {
  const msg = JSON.parse(frame.body);
  renderMessage(msg);                       // type으로 스타일 분기
  if (msg.live) renderScoreboard(msg.live); // 골 메시지면 스코어보드도 갱신
});
```

재연결로 메시지를 놓쳐도 **REST 한 번이면 스코어보드가 복구**된다. `live`가 항상 전체 스냅샷이라 누적 계산이 없기 때문이다.

### 6.8 계약상 짚어둘 것

1. **`matchId`는 계속 FotMob ID다.** 네이버 gameId는 서버 내부에만 존재하고 프론트로 나가지 않는다. 매핑이 깨져도 채팅방 키는 흔들리지 않는다.
2. **"매치봇"을 닉네임 예약어로 막아야 한다.** 막지 않으면 유저가 선점해 가짜 골 알림을 칠 수 있다. 기존 금칙어 필터에 추가한다.
3. **`scorers`는 항상 전체 목록**이다. "새로 추가된 골"만 주지 않는다. 프론트는 매번 통째로 다시 그리면 되고, VAR로 줄어드는 경우도 자연히 처리된다.
4. `ipHash`는 봇 메시지에서 `null`이다. 프론트가 동일인 식별에 쓰고 있다면 null 체크가 필요하다.
5. **`type`이 늘어날 수 있다.** 프론트는 아는 타입만 채팅 라인으로 그리고 나머지는 `live`만 꺼내 써야 한다 — 지금 프론트가 `type === 'USER'`인 것만 그리므로 `STATUS` 추가에 프론트 변경이 필요 없었다.

## 7. matchId ↔ gameId 매핑

**유일한 실질 구현 부담이다.**

채팅방 키는 FotMob matchId인데, 네이버 gameId는 `Z5BQDTTiMjv6iBO` 같은 불투명 문자열이라 서로 무관하다.

1. 킥오프 전(기존 `scheduledUpdate` 시각에 편승) `schedule/calendar`로 해당 월 경기를 긁는다.
2. 팀명에 `AT 마드리드`가 포함된 경기를 찾는다.
3. 킥오프 시각(±30분)으로 FotMob `UpcomingMatch`와 대조해 짝을 짓는다.
4. `live:map:{matchId}`에 `naverGameId`를 저장한다.

상대팀 표기가 FotMob과 다르므로(`AT 마드리드` vs `Atletico Madrid`) 매핑 테이블이 필요하지만, **관리 대상은 아틀레티가 만나는 팀 20여 개뿐**이라 부담이 작다. 킥오프 시각 대조를 1차 기준으로 삼으면 이름 매칭 실패에도 견딜 수 있다.

## 8. 주의점

1. **VAR 취소** — 스코어는 덮어쓰기, 골 목록은 Set 비교로 정정. 5.3 참고.
2. **자책골** — `ownGoal: true`를 무시하면 상대 선수를 우리 득점자로 표시하는 사고가 난다.
3. **비공식 API** — 네이버·FotMob 모두 계약된 API가 아니라 예고 없이 바뀐다. FotMob은 이미 경로가 한 번 옮겨졌다. 조용히 실패하지 않도록 알림을 붙이고, 네이버가 깨지면 FotMob으로 자동 폴백하도록 둔다(느리지만 동작은 함). → **구현 완료, 8.6 참고**
4. **법적 검토** — 국내 서비스이므로 상업화·규모 확대 시 정식 계약 여부를 재검토한다.
5. **장애 시 동작** — 라이브 정보는 부가 기능이다. 실패해도 **채팅 자체는 정상 동작해야 한다.** try-catch로 감싸고 WARN 로그만 남기는 fail-open으로 간다.

### 8.6 FotMob 폴백 (구현됨)

한 줄 요약: **네이버가 안 되면 FotMob으로 내려가되, 골 목록은 이름이 아니라 「팀 + 분」으로 맞춰 이어붙인다.**

#### 내려가는 조건

| 상황 | 동작 |
|---|---|
| gameId 매핑 없음 | **즉시** 폴백. FotMob은 matchId를 그대로 쓰므로 매핑 실패가 장애가 아니다 |
| 네이버 연속 3회 실패 | 폴백. 한 번씩 나는 타임아웃으로 갈아타면 두 소스를 계속 오간다 |
| 네이버 429 | 폴백. 막고 있는 상대를 계속 두드리는 것보다 낫다 |

한 번 내려가면 **5분은 버틴다.** 그 사이 폴링 주기는 5초가 아니라 **15초** — 응답이 70배 크고(180KB 대 2.6KB) CDN 캐시까지 붙어 있어 촘촘히 불러도 같은 값이 온다.

#### 골 키가 호환되지 않는 문제

골 키에는 선수 이름이 들어가는데 네이버는 한글, FotMob은 영문이다.

```
네이버 : A|43+0|호르헤 도밍게스|false
FotMob : A|43+0|Jorge Domínguez|false     ← 같은 골, 다른 키
```

그대로 비교하면 **이미 알린 골 전부가 "새 골"로, 옛 키 전부가 "VAR 취소"로 쏟아진다.**
그래서 소스가 바뀐 첫 턴에는 이름 대신 **팀(`isHome`) + 절대 분(±2분)** 으로 짝을 맞춘다.

- 짝이 있으면 → 이미 알린 골. 조용히 넘긴다
- 짝이 없으면 → 소스가 끊긴 동안 들어간 골. 지금 알린다
- **취소는 이번 턴에 알리지 않는다** — 짝 없는 옛 키가 VAR 취소인지 두 소스의 기록 차이인지 구분되지 않는다. 없는 취소를 알리는 쪽이 더 나쁘다

소스 표식은 `live:src:{matchId}`에 둔다 (설계 표에 없는 키, 구현 중 추가).

#### 감수하는 것

- **선수 이름이 영문으로 바뀐다.** 폴백을 쓰는 값이다. 팀 이름은 직전 네이버 스냅샷의 한글 표기를 이어 써서 스코어보드가 통째로 튀지는 않게 했다.
- **CDN 캐시.** 2026-08-11 확인 시 `max-age=3600`이었다. 설계 2.2에 적힌 `max-age=10`은 더 이상 맞지 않는다. **다만 확인한 두 경기가 각각 종료·미시작 상태였다** — 정적인 데이터라 길게 잡혔을 가능성이 크고, FotMob 자체 화면이 라이브로 동작하는 이상 경기 중에는 짧을 것으로 본다. 폴백 호출마다 응답의 `cache-control`을 로그로 남기게 해 뒀으니 **8/15에 실제 값을 확인한다.** 라이브 중에도 3600이면 이 폴백은 스코어 확인용 정도이지 골 알림용은 못 된다.

## 9. 측정 절차

`scripts/measure-live-feed.js`가 4.3의 재측정과 아래 미검증 항목 수집을 함께 수행한다.

### 9.1 사용법

```bash
node scripts/measure-live-feed.js --find              # gameId 목록 확인
node scripts/measure-live-feed.js QyRcDHa8DA07hWz     # 측정 시작 (킥오프 10분 전 실행)
```

1. 킥오프 전에 실행해 둔다. 기본 2초 주기로 폴링하며 골·상태 변화 시각을 기록한다.
   (측정용이므로 운영값 5초보다 촘촘하게 잡는다 — 반영 시각을 정밀하게 찍기 위해서다)
2. **중계 화면에서 골을 본 순간 터미널에 Enter**를 친다. 메모를 남기려면 글자를 치고 Enter.
3. 경기 종료 후 Ctrl+C. 피드 반영 시각과 화면 확인 시각이 짝지어진 결과표와 평균 격차가 출력된다.
4. 전체 기록은 `scripts/live-measure-{gameId}.jsonl`에 남는다.

판정 기준은 스크립트가 자동 출력한다. 평균 격차가 **+20초를 넘으면** 지연 버퍼 도입을 재검토한다.

### 9.2 이 경기에서 함께 확인할 것

작성 시점에 진행 중인 경기가 없어 아래는 확인하지 못했다. 스크립트가 자동으로 기록한다.

| 항목 | 기록되는 위치 |
|---|---|
| 경기 중 `statusCode` / `statusInfo` 실제 값 | `status_change` 레코드 — `statusInfo`는 8/20에 확인됨(`전반종료`), `statusCode`는 여전히 미확인 |
| 라이브 중 `scorers`가 실시간으로 채워지는지 | `feed_goal` 레코드 유무 |
| 네이버의 실제 반영 지연(초) | 결과표의 평균 격차 |
| 네이버 rate limit 임계값 | `rate_limit` 레코드 (429 발생 시) |
| 라이브 중에도 `no-cache`가 유지되는지 | 모든 레코드의 `cacheControl` |
| 응답 크기·응답 시간 | 모든 레코드의 `bytes` / `durationMs` |

### 9.3 로컬 리허설 — `scripts/fake-live-match.js`

측정(9.1)은 실제 경기가 있어야 하지만, **구현이 맞게 도는지는 경기 없는 날에도 확인할 수 있다.**
네이버·FotMob 자리에 가짜 서버를 앉히고 대본대로 골을 넣어 주는 방식이다. 앱은 자기가
진짜 경기를 보고 있다고 믿으므로 **코드 경로가 운영과 100% 같다.**

```bash
docker run -d --name atleti-redis -p 6379:6379 redis:7-alpine   # 없으면 먼저
node scripts/fake-live-match.js                                  # 터미널 1
./gradlew bootRun --args='--spring.profiles.active=h2,livedemo'  # 터미널 2
```

앱이 뜨면 스크립트가 일정 동기화를 대신 눌러 주고, 120초 뒤 킥오프부터 대본이 돌아간다.
스크립트가 `GET /api/chat/9999999`를 읽어 **유저가 보게 될 채팅 라인과 스코어보드를 그대로 출력**한다.

대본은 **테스트용이라 일부러 말이 안 되게 몰아친다 — 분당 3골, 골 16건 + VAR 취소 3건, 최종 7-6.**
많이 넣는 게 목적이 아니라 폴러가 무너질 만한 자리를 골라 넣은 것이다:

| 대본 | 확인하는 것 |
|---|---|
| 킥오프 전 → 경기중 | 킥오프 전 60초 폴링, `경기전` 스냅샷 (6.2) |
| **2~3초 간격 버스트** | 폴링 주기(5초)보다 촘촘하다 → **한 턴에 여러 골**이 잡힐 때 다 나가는지 |
| **58′ 알바레스 + 58′ 코케** | 같은 분·같은 팀 두 골. 골 키가 선수 이름으로 갈리는지 (5.3) |
| **목록 중간 골 취소** | 마지막이 아니라 가운데 항목이 사라진다 → 점수 역전 |
| **취소 번복** | 지웠던 골이 되살아난다. `SREM` 뒤 `SADD`라 다시 알려야 정상 |
| **전반 4′ 골을 후반에 취소** | 한참 지난 골의 VAR 취소 |
| 양쪽 자책골 | `(자책골)` 표기 + 점수가 넣은 선수의 **반대편**에 붙는지 (8.2) |
| 45+3′ / 90+4′ / 90+7′ | 추가시간 표기 |
| 경기종료 | 종료 감지 → +10분 뒤 폴링 중단 (5.4) |

경기가 끝난 뒤 `s`를 누르면 **대본이 기대하는 알림 수와 실제 채팅방 알림 수를 대조해 판정**한다.
어긋나면 많은지 적은지에 따라 어디를 볼지 짚어 준다 (중복 발행 / 놓친 골 / 없는 취소).

터미널 키로 장애도 만들 수 있다:

- **`k`** — 네이버를 503으로 죽인다. 연속 3회 실패 후 FotMob으로 내려가는지, 그때 **이미 알린 골이 다시 안 나오는지**(8.6 골 정렬) 확인한다. 선수 이름이 영문으로 바뀌는 것도 여기서 보인다
- **`r`** — 살린다. 폴백 유지 시간(5분)이 지난 뒤 네이버로 되돌아오는지 확인한다

프로파일은 `livedemo` 하나로 상류 주소만 갈아끼운다(`atleti.source.*-base-url`).
기본값이 실제 주소라 **운영에는 아무 영향이 없다.**

> **순서 주의 — 앱을 먼저 띄운다.** 스크립트의 킥오프 카운트다운(120초)은 *스크립트가*
> 뜬 순간부터 흐른다. 앱 부팅이 그보다 오래 걸리면 동기화 시점에 킥오프가 이미 지나서
> `scrapeUpcomingMatches`의 "과거 경기는 버린다" 필터에 걸리고, 일정이 0건으로 잡혀
> 폴러가 영영 안 깬다(`⏳ 폴러가 이 경기를 잡을 때까지 기다립니다`에서 멈춘다).
> 앱을 먼저 올리고 `/api/chat/9999999`가 200을 주면 그때 스크립트를 띄운다.

### 10.2 8/15 마르세유전 결과 — 실사용에서 드러난 것

> 조사 과정과 배제한 가설까지 담은 전체 기록은 [live-match-8-15-postmortem.md](live-match-8-15-postmortem.md)에 있다.

측정 스크립트는 띄우지 않았고, 방을 직접 쓰면서 눈으로 본 기록이다.
**1번(골 알림 도달)은 됐다.** 나머지에서 세 가지가 나왔다.

| 증상 | 원인 | 조치 |
|---|---|---|
| 킥오프 직후 시계가 쿠팡플레이보다 **90~95초 빨랐다.** 첫 골이 나온 뒤 맞춰졌다 | 화면이 **예정** 킥오프로 세고 있었다. 실제 킥오프가 그만큼 늦었던 것 | 아래 ㉠㉡ |
| 하프타임에 **시계가 안 멈췄다** | 서버는 `firstHalfEnded`를 받아 스냅샷에 넣어 뒀는데, 프론트로 나가는 통로가 골 알림뿐이라 골 없는 하프타임에는 아무것도 안 나갔다 | ㉠ |
| 골 연출 중 친 채팅이 **연출이 끝난 뒤에** 올라왔다 | 서버 경로에는 지연 요소가 없다(아래) | 미해결 — 재현 필요 |

**㉠ 상태 변화 브로드캐스트 (6.5).** `status`·`periods`가 바뀐 턴에 `STATUS` 메시지를 발행한다.
근본 원인은 하나였다 — 스코어보드를 갱신할 통로가 골 알림밖에 없었다. 첫 증상에서
"첫 골이 나온 뒤 맞춰졌다"는 것도 같은 이야기다. **골이 기준점을 나르는 배달부였다.**

**㉡ 시계 조회 간격을 구간별로 나눴다.** FotMob에 시계를 다시 묻는 주기가 60초 고정이었다.
화면의 시계가 실제로 틀어져 있는 구간(기준점 미확보·하프타임·전반 43분 이후)만 15초로
좁히고 나머지는 60초를 유지한다. 전반 한복판에는 기준점이 안 바뀌므로 자주 물어도 소용없다.

**㉢ 상태가 바뀐 턴에는 간격을 무시하고 FotMob에 바로 묻는다.** 리허설에서 잡힌 것이다 —
㉡까지만 넣었더니 **하프타임이 통째로 지나간 뒤에야** `firstHalfEnded`가 도착했다.
㉡의 "전반 43분 이후" 조건이 벽시계 기준이라 압축된 리허설에서는 안 걸렸기 때문인데,
실경기에서 걸리더라도 **더 빠른 신호를 놔두고 있었다: 네이버의 상태 변화 자체.**
네이버는 5초마다 보고 있어 하프타임·후반 시작을 그 안에 알려주지만 시계 기준점은
FotMob에만 있다. 상태가 바뀐 턴에 재조회 간격을 건너뛰게 하니 셋 다 3초 안에 도착했다.

㉡의 43분 조건은 그대로 둔다. 상태로 못 잡으면 시간으로 잡는 이중 안전장치가 필요하다.

> **2026-08-20 추가.** 당시 "네이버의 실제 하프타임 표기를 모른다"는 이유로 43분 조건을
> 남겨 뒀는데, 표기는 **`전반종료`**로 밝혀졌다. 그리고 그 표기가 종료 판정의
> `contains("종료")`에 걸려 **폴러를 통째로 멈춰 세웠다** — 후반 골이 하나도 안 나갔다.
> 경위와 수정은 [round1.md](round1.md). 리허설이 지어낸 `하프타임`을 쓰고 있었던 것이
> 이 함정을 통과시킨 직접 원인이다.

**남은 오차 약 5초.** 보정 뒤에도 시계가 쿠팡플레이보다 5초쯤 느렸다. 쿠팡플레이 자체가
실제보다 ~5초 늦으므로(4.2) 우리 기준점이 실제 킥오프보다 ~10초 늦게 찍혀 있다는 뜻이다.
FotMob의 `firstHalfStarted`도 사람이 누르는 값이라 여기가 바닥이다. **상수로 당기지 않았다** —
소스마다 다를 값을 한 경기 관측으로 못 박으면 다음 경기에서 반대로 틀어진다. 8/20에 재측정한다.

**채팅 지연은 서버가 아니다.** 유저 메시지와 골 알림은 `ChatService.store()` → Redis
List → `convertAndSend` → `ChatMessageRelay` → `/topic/chat/{matchId}`로 **완전히 같은 길**을
간다. 락도 큐도 배치도 없고, 골이 유저 메시지를 밀어내는 구조가 없다. 프론트에서도
`celebrating` 상태가 피드 렌더를 막는 자리는 찾지 못했다. 남은 가설은 5초짜리 연출
동안 캔버스 셋(LED 링·조명·색종이)이 메인 스레드를 잡는 것인데, **측정 전에는 추측이다.**
9.3의 리허설로 재현해서 확인한다 — WebSocket 프레임 도착 시각과 화면에 뜬 시각을 나란히 찍으면
"늦게 왔다"와 "늦게 그렸다"가 갈린다.

## 11. 화면 표기 (구현하며 추가)

한 줄 요약: **채팅은 한글, LED 보드는 로마자.** 같은 골을 두 가지로 그리는 것이지 데이터를 바꾸는 게 아니다.

보드는 "직관 온 느낌"을 만드는 장치라 실물 경기장처럼 라틴 표기여야 하는데, 주 소스인 네이버는
한글만 준다. 그래서 **FotMob의 같은 경기에서 로마자 표기를 가져와 스냅샷에 얹는다.**
이미 폴백용으로 부르고 있던 API라 추가 비용이 거의 없고, 덤으로 폴백 경로가 매 경기 점검된다.

### 11.1 득점자 이름

음역표를 만들지 않는다. **같은 경기 같은 분에 들어간 골은 같은 골**이므로 팀(`isHome`)과
분(±2)으로 짝이 지어진다.

```
네이버 :  43' "호르헤 도밍게스"     ─┐
                                  ├─ 같은 골 → nameLatin = "Jorge Domínguez"
FotMob :  43' "Jorge Domínguez"  ─┘
```

이적시장 영입도 유스 콜업도 등록 없이 그대로 동작한다. 짝을 못 찾으면 **비워 둔다** —
엉뚱한 이름이 보드에 뜨는 건 버그가 아니라 오보다. 화면은 자체 표 → 이름 생략 순으로 물러선다.

`nameLatin`은 **골 키에 넣지 않는다.** 이름이 뒤늦게 채워질 때 키가 바뀌면 이미 알린 골을 다시 알린다.

### 11.2 경기 시계

`live.kickoff`(예정)만으로 세면 킥오프 지연·하프타임 길이·전반 추가시간만큼 어긋난다.
FotMob `header.status.halfs`가 **실제로 공이 굴러간 시각**을 주므로 그것을 기준점으로 쓴다.

```
후반 시계 = 45:00 + (지금 − secondHalfStarted)
```

**`halfs`에는 타임존이 없다.** 실측은 UTC+2였지만 못 박으면 표기가 바뀌는 순간 몇 시간 틀어지므로,
같은 응답의 `utcTime`(UTC 명시)과 대조해 오프셋을 역산한다. 잔차(=킥오프 지연)가
`-5 ~ +30분`을 벗어나면 해석을 버리고 예정 킥오프로 되돌아간다 — 틀린 시각을 자신 있게
띄우느니 어림하는 편이 낫다.

### 11.3 팀명·대회명

같은 방식으로 `homeTeamLatin`·`awayTeamLatin`·`competitionLatin`을 실어 보낸다
(FotMob `general.homeTeam.name`, `general.leagueName`).

- **아틀레티는 어떤 표기로 오든 `ATM`.** 전용 채팅방인데 우리 팀 약칭이 흔들리면 버그로 보인다
- 약칭이 알려진 팀은 그 약칭(RSO·VIL), 아니면 라틴 이름 **앞 세 글자**(MAR·MAL)
- 라틴을 못 받았고 한국어뿐이면 `RIV` — 초성을 따면 보드에 한글이 뜬다
- 대회명은 판단이 안 되면 **경기장 이름**으로 대신한다 (실물 보드도 그 자리를 돌려 쓴다)

> 여기서 걸린 함정 두 개. **네이버는 아틀레티를 `AT 마드리드`로 준다**(3.3) — 프론트 표에
> 그 표기가 없어 우리 팀이 `RIV`로 나왔다. 그리고 표의 키에 악센트가 든 채였는데
> 조회 키는 악센트를 지워서(`atléticodemadrid` ≠ `atlticodemadrid`) 영원히 안 맞았다 —
> `ATLÉTICO DE MADRID`가 `ATL`로 나온 원인이다. 표는 정규화한 키로 펴서 쓴다.
