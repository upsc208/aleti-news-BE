## 왜 재야 하나 — 팬아웃은 제곱으로 는다

접속자 N명, 1인당 초당 m건을 치면 서버가 내보내야 하는 건수는 **N × m × N**이다.

| 접속자 | 1인당 전송 | 서버가 내보내는 양 |
|---|---|---|
| 20명 | 0.05건/초 (20초에 한 번) | 초당 20건 |
| 50명 | 0.1건/초 | 초당 250건 |
| 200명 | 0.1건/초 | **초당 4,000건** |
| 200명 | 0.5건/초 (골 터진 직후) | **초당 20,000건** |

서버는 **1 vCPU · RAM 1GB · 힙 400MB**다(OCI E2.1.Micro). 브로커는 인메모리
`SimpleBroker` 한 개이고 그 팬아웃이 전부 이 한 코어에서 돈다. 20명은 여유롭고 200명은
못 버틸 가능성이 크다 — **그 경계가 어디인지 아무도 모르는 것**이 지금 상태다.

## 무엇을 재나

보내는 쪽이 메시지 본문에 **보낸 시각을 박고**, 받는 쪽이 도착 시각과 뺀다. 한 대에서
전부 돌리므로 시계가 하나라 시각 동기화 문제가 없다.

| 값 | 뜻 |
|---|---|
| 연결 성공 / 실패 / 도중 끊김 | 지연보다 **먼저 터지는 것**이 이쪽이다 |
| 브로드캐스트 지연 p50 / p95 / 최대 | 보낸 순간부터 남들 화면에 뜨기까지 |
| 초당 수신 건수 | 서버가 실제로 뿜어낸 양 |
| 서버 거절 건수 | 도배 상한에 걸린 수 |

### 판정 기준

| 지연 p95 | 판단 |
|---|---|
| 500ms 이하 | 사람이 못 느낀다. 통과 |
| 500ms ~ 2초 | 느껴지지만 대화는 된다. 여기가 나오면 그 접속자 수가 **실질 상한**이다 |
| 2초 초과 | 대화가 끊긴 것처럼 보인다. 그 수는 못 받는다 |

**연결 실패나 도중 끊김이 0이 아니면 지연을 보기 전에 그것부터 본다.** 지연이 아무리 좋아도
못 들어온 사람은 못 들어온 것이다.

## 실행

```bash
# 1) 자유방에 50명, 그중 5명이 채팅 (평시 확인)
node scripts/chat-load-test.js --url https://atleti.kr --clients 50 --senders 5 --seconds 30

# 2) 계단식으로 천장 찾기 — 50 → 100 → 200 → 300
node scripts/chat-load-test.js --url https://atleti.kr --clients 100 --senders 10 --seconds 60
node scripts/chat-load-test.js --url https://atleti.kr --clients 200 --senders 20 --seconds 60
```

**서버에서 같이 볼 것** (다른 창에서):

```bash
ssh -i ~/.ssh/atleti-deploy-key ubuntu@168.110.106.79 \
  "top -b -n 30 -d 2 | grep -E 'java|Cpu|Mem'"
```

CPU가 100%에 붙어 있으면 그게 천장이다. 메모리가 스왑으로 넘어가면 그 순간부터 지연이
계단식으로 뛴다.

### 두 가지 함정

**㉮ 한 대에서 돌리면 IP가 하나다.** 도배 상한은 IP당 10초에 10건(`RATE_LIMIT_MAX`)이라,
이 스크립트의 모든 연결이 그 한 창을 나눠 쓴다. 전송 속도를 올려도 서버가 거절할 뿐이다
(결과의 "서버 거절"에 잡힌다). **골 순간의 동시 전송을 그대로 재려면** 여러 대에서 나눠
돌리거나 시험용으로 상한을 잠시 올려야 한다.

다만 부하의 본체는 **수신자 수**다. 전송이 느려도 팬아웃 천장은 그대로 보인다.

**㉯ 경기방은 닫혀 있으면 다 거절한다.** 방은 킥오프 1시간 전에 열린다. 평시 측정은
자유방(`--room free`, 기본값)으로 한다.

## 스크립트에 대해 확인된 것 / 안 된 것

**확인됨** — 프레임 조립·해석 4종(STOMP 프레임, SockJS `a[...]` 벗기기, 헤더 파싱, 지연
추출 정규식)을 단위로 통과시켰다. 연결이 안 되는 대상에 걸었을 때 실패 수를 정확히 세고
빠져나오는 것도 확인했다(초기 판에는 닫힌 소켓을 다시 닫으며 초당 수천 번 도는 버그가 있었다).

**미확인** — **실제 서버와 붙여본 적이 없다.** SockJS raw WebSocket 통로(`/ws/websocket`)의
프레임 형식은 규약대로 맞췄지만 검증은 첫 실행이 처음이다. 만약 연결 성공이 0으로 나오면
순서대로 본다.

1. 서버 로그에 403이 보이면 **출처 검사**다 → `--origin https://atleti.kr`
2. `CONNECTED`가 안 오면 **프레임 형식**이다 → 서버가 받은 원문을 로그로 찍어 비교
3. 그래도 안 되면 `ChatRoomIntegrationTest`가 쓰는 스프링 STOMP 클라이언트로 갈아탄다
   (그쪽은 이 저장소에서 이미 동작이 증명된 경로다)

## 같이 바뀐 것 — 도배 상한 5 → 10건

부하와 별개로, 상한이 **IP 단위**라는 점이 쇼케이스에서 문제가 된다. 모바일은 통신사
NAT라 수십 명이 같은 공인 IP로 보이고, 그 사람들이 10초 창 하나를 나눠 쓴다. 골이 터져
다 같이 치는 30초가 정확히 그 상황이다.

10초에 10건은 사람이 손으로 칠 수 있는 속도의 위쪽이라 도배는 여전히 막힌다.

**근본 해결은 아니다.** NAT 뒤 인원이 더 많으면 10건도 나눠 갖는다. 남은 선택지는 리밋 키를
`clientId` 우선(IP는 훨씬 느슨한 2차 상한)으로 바꾸는 것인데, `clientId`는 클라이언트가 주는
값이라 마음먹으면 우회된다. **쇼케이스 뒤에 판단한다** — 실제로 거절이 얼마나 났는지
로그로 보고 정하는 편이 낫다.
