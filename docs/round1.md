## ③④는 같은 원인이다 — `"전반종료".contains("종료")`

```kotlin
// 문제의 코드
FINISHED_LABELS = listOf("종료", "취소", "연기", "몰수")
isFinished = ... || FINISHED_LABELS.any { game.statusInfo.contains(it) }
```

네이버의 하프타임 표기가 **`전반종료`**였다. 부분 문자열 검사가 여기서 `종료`를 찾아내
경기가 끝난 것으로 판정했고, 폴러는 이 경기를 "끝난 경기"로 표시한 뒤 폴링을 멈췄다.

운영 서버 스냅샷에 증거가 그대로 남아 있었다.

```json
{ "status": "전반종료", "homeScore": 0, "awayScore": 0, "scorers": [],
  "periods": { "firstHalfStarted": "19:08:20Z", "firstHalfEnded": null },
  "updatedAt": "20:08:25Z" }
```

`updatedAt`이 전반 종료 직후에 멈춰 있다. 그 뒤로 서버는 이 경기를 쳐다보지도 않았다 —
후반 골을 감지할 폴러가 없었으니 ④가 나온 것이고, `firstHalfEnded`를 영영 못 받았으니
③이 나온 것이다.

**리허설이 이걸 왜 못 잡았나.** 가짜 서버가 하프타임 표기로 내가 지어낸 `하프타임`을
쓰고 있었다. 실제 값을 몰라 그럴듯한 값을 넣어 뒀던 것인데, 그 바람에 리허설이 이
함정을 그대로 통과시켰다. **지어낸 데이터로 검증한 대가다.**

### 고친 것

**㉮ 부분 일치 → 정확 일치.** 공백만 지우고 `{경기종료, 종료, 경기취소, 취소, 연기, 몰수}`에
정확히 들어맞을 때만 끝난 것으로 본다. 모르는 표기(`후반종료` 등)는 **안 끝난 것으로 본다** —
늦게 멈추면 폴러가 킥오프 +3시간에 어차피 끝나지만, 일찍 멈추면 이번처럼 경기가 통째로 날아간다.

**㉯ 하프타임이면 `statusCode`와 무관하게 종료가 아니다.** 8/20 하프타임의 실제 코드가
무엇이었는지 기록이 없어서, 그게 종료 코드였을 가능성을 아직 못 지웠다. 표기가 `전반종료`인데
코드 때문에 또 멈추면 같은 사고가 난다. 그래서 하프타임 판정이 코드보다 우선한다.

**㉰ 시계 기준점을 네이버 상태로 메꾼다.** ㉮만으로는 시계가 안 살아난다 — FotMob의
`halfs.firstHalfEnded`가 **하프타임 15분이 지나도록 끝내 안 왔다**(CDN 캐시로 추정, 설계 8.6).
폴링이 살아 있었어도 시계를 멈출 값 자체가 없었다. 그래서 FotMob 하나에 매달리지 않는다:

- 네이버가 `전반종료`를 주면 그 시각을 `firstHalfEnded`로 (오차는 폴링 주기 5초 안쪽)
- 다시 `경기중`이 되면 `secondHalfStarted`로 → 화면이 45:00부터 다시 센다
- **FotMob 값이 오면 그쪽이 이긴다.** 비어 있을 때만 채운다
- 전반 시작 시각조차 모르면 아무것도 지어내지 않는다

## ① 세레머니 — 공이 안 굴렀는데 시계가 돌았다

화면은 실제 시작 시각(`periods.firstHalfStarted`)이 없으면 **예정 킥오프**로 어림한다.
그래서 04:00이 되자마자 시계가 돌기 시작했고, 실제 킥오프까지 8분 20초 동안 틀린 값을
자신 있게 띄웠다. 서버는 `경기전`이라고 말해주고 있었는데 화면이 그걸 안 보고 있었다.

**고친 것:** `formatMatchClock`이 서버 상태를 본다. `경기전`이면 어림하지 않고 `null`을
돌려주고, 보드는 후원 화면(OFF)으로 남는다 — 실물 링이 경기 전에 그러는 모습 그대로다.
상태를 모르면 예전대로 동작한다(서버가 상태를 안 줄 때 시계를 통째로 끄면 안 되므로).

## ② 우리가 중계보다 빠르다 — 라이브 정보 전체를 30초 뒤로 민다

우리 시계는 실제 킥오프에 맞춰져 있으니 거의 실시간이다. **중계가 그만큼 느린 것이다.**
설계 4.3이 "라리가는 스페인 제작 → 국제 전송 → 한국 재인코딩이라 중계 경로가 길다"고
예측한 것이 첫 측정에서 확인됐다 (8/15 프렌들리는 5초였다).

봇이 시청자보다 빠르면 실시간 정보가 아니라 **스포일러**다. 실제 골을 0초로 두면:

```
0초        ⚽ 실제 골
+2~15초    📡 네이버 반영 (현장 기록원 + 제공사, 설계 4.1)
+0~5초     🔄 우리 폴링 주기
  ↓
+2~20초    📱 우리 알림          ← 시청자보다 7~31초 빠르다
+27~33초   🖥️ 쿠팡플레이 화면
```

### 얼마를 미나 — 30초

네이버 반영 시간이 골마다 달라서(2~15초) 고정 지연으로 정확히 맞출 수는 없다. 그래서
**가장 빨리 반영된 경우에도 시청자를 앞지르지 않는 값**을 고른다.

| 지연 | 알림 도착 | 시청자 대비 |
|---|---|---|
| 20초 | +22~40초 | 8초 빠름 ~ 10초 늦음 → 스포일러 남음 |
| 25초 | +27~45초 | 3초 빠름 ~ 15초 늦음 → 아슬아슬 |
| **30초** | **+32~50초** | **2~20초 늦음 → 앞지르지 않는다** |
| 40초 | +42~60초 | 12~30초 늦음 → 너무 늦다 |

최악이 20초 늦는 것인데, 스포일러보다 낫다.

### 무엇에 거나 — 전부

시계만 밀면 **스코어보드 숫자가 먼저 올라가** 똑같이 새어 나간다. 그래서 시계·스코어·
득점자·골 알림·하프타임에 **모두** 같은 폭으로 건다. 화면이 한 몸으로 움직인다.

```properties
atleti.live.delay-seconds=${LIVE_DELAY_SEC:30}
```

손잡이는 **하나뿐이다.** 둘로 나누면 값이 어긋나는 순간 화면이 따로 논다.
`0`을 넣으면 8/20 이전 동작으로 돌아간다.

### 어떻게 거나 — 발행이 아니라 입력을 늦춘다

폴러가 가져온 스냅샷을 대기열에 넣고 **30초 묵은 것**을 꺼내 기존 diff 로직에 태운다.
스냅샷은 매번 전체 상태라, 늦은 입력을 그대로 태우면 골·취소·상태 변화가 저절로 같이 밀린다.
발행만 따로 보류하면 "취소가 골보다 먼저 나가는" 순서 문제를 직접 풀어야 한다.

- **라틴 이름·시계 기준점 확보는 실시간으로 유지한다.** 특히 하프타임 기준점은 그 순간
  시각으로 찍혀야 정확하다. 늦추는 것은 그다음 단계다
- 시계는 기준점 셋을 **통째로** 민다. 하프타임에 멈추는 값은
  `firstHalfEnded − firstHalfStarted`라 **차이**이므로 그대로다
- 내부 판단(폴링 간격·하프타임 감시)에는 안 쓴다. 그쪽까지 밀면 경기 진행보다 늦게 반응한다
- **덤:** 넣자마자 VAR로 취소된 골은 **아예 안 나간다.** 두 변화가 같은 대기 구간에서
  상쇄되기 때문인데, 시청자가 보지도 못한 골을 알렸다 취소하는 것보다 낫다
- 대기열은 인스턴스 메모리에 둔다. 재시작하면 30초쯤 발행이 쉬었다가 이어진다

부수 효과로 실제 킥오프 후 30초 동안 보드가 OFF로 남는데, 시청자가 아직 킥오프를 못 봤으니
그게 맞는 동작이다.

> **값은 한 경기 눈대중이다.** 8/15 프렌들리는 격차가 5초였으니 국내 제작 중계나 다른
> 대회에서는 30초가 과하다. 재배포 없이 `.env`만 고치면 된다.

## ⑤ `vs 마르세유` — 지난 경기 상대가 떴다

```js
const opponent = match ? (match.isHome ? match.awayTeam : match.homeTeam) : null;
```

`match`는 **"가장 최근에 끝난 경기"**(8/15 마르세유)다. 지금 보고 있는 경기(`live`)를 안 썼다.
서버 데이터는 `말라가`로 정확히 갔다.

**고친 것:** `live`를 1순위로 두고 `match`는 폴백으로 밀었다.

## 검증

리허설을 **실경기와 같은 조건**으로 돌렸다 — 대본이 이제 실제 표기 `전반종료`를 쓰고,
`--nohalfs`로 FotMob이 `halfs`를 안 주는 상황까지 재현한다.

```
09:31:06  대본: 전반 종료 (FotMob은 halfs 미제공)
09:31:11  전반 종료를 네이버 상태로 잡았습니다 (전반종료) — FotMob 미제공
09:31:11  상태 변화 발행: 경기중 → 전반종료 [code=HALFTIME]
          firstHalfEnded = 09:31:11   ← 시계가 여기서 멈춘다
```

**5초 만에** 잡혔다. 실경기에서는 이 값이 15분 뒤까지도 `null`이었고 그 전에 폴러가 죽어 있었다.
골 7건 + VAR 취소 1건도 전부 정상 발행됐고, 라틴 이름은 `이강인 → Kang-In Lee`까지 매칭됐다.

단위 테스트로 못 박은 것: `전반종료`는 종료가 아니다 / `경기종료`는 종료다 / 모르는 표기는
안 끝난 것으로 본다 / 시계 지연이 기준점 셋을 같은 폭으로 민다 / 하프타임 정지 값은 안 바뀐다.

## 다음 경기에 확인할 것

1. **골 알림이 실제로 나가는지** — 이번에 통째로 죽었던 기능이다
2. **하프타임에 시계가 멈추고 후반에 45:00으로 돌아가는지**
3. **시계·골 알림이 쿠팡플레이보다 뒤인지, 얼마나 뒤인지** — 과하거나 모자라면

4. **하프타임의 네이버 `statusCode`** — 로그에 `[code=...]`로 남는다.
   아틀레티 경기를 기다릴 것 없이 **아무 경기나 하프타임일 때** 네이버 API를 찔러 보면 된다
5. **세레머니가 있으면 킥오프 전까지 보드가 OFF로 남는지** (①) — 8/20에 8분 20초였다
6. 8/15의 미해결 항목: **골 연출 중 채팅이 늦게 뜨는지** (모바일).
   8/20에는 골 알림 자체가 안 나가서 확인 기회가 없었다

## 표기가 대회마다 다르다는 것

`전반종료`를 알아내면서 같이 확인된 것이다 — 라리가는 경기 전이 `경기전`인데 K리그는
`시작전`이다. **라리가에서 맞춘 표기가 다른 대회에서도 맞으리라는 보장이 없다.**

그래서 모르는 표기가 들어오면 이렇게 동작하게 해 뒀다.

| 판정 | 모르는 표기일 때 | 왜 |
|---|---|---|
| 종료인가 | **아니다** (계속 폴링) | 늦게 멈추면 +3시간에 어차피 끝난다. 일찍 멈추면 경기가 통째로 날아간다 |
| 하프타임인가 | 아니다 | 43분 시간 조건이 백업으로 남아 있다 |
| 공이 굴렀나 | **굴렀다** (예전처럼 어림) | 시계를 통째로 끄면 진행 중인 경기에서 보드가 죽는다 |

셋 다 **모르면 기능이 죽지 않는 쪽**으로 기울여 뒀다.
