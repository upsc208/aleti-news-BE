# 금칙어 필터링 시스템 설계서 (Profanity Filtering Design)

> **작성일**: 2026-07-30 (최종 수정: 2026-07-31 — 연락처 차단 5장, 화이트리스트 주의점 3.2 추가)  
> **대상 환경**: Spring Boot 3.4 + Kotlin, Redis 7.x, 라이브 채팅 (매치데이 동접 200명 이상)  
> **참고 모델**: 배달의민족 통합금칙어시스템 (우아한형제들 기술블로그)  
> **브랜치**: `feat/LiveChat`

---

## 1. 개요 및 배경

매치데이 라이브 채팅 및 닉네임 생성 시 부적절한 단어(비속어, 욕설, 차별/혐오 표현, 사칭 키워드)를 사전 차단하여 건전한 대화 환경을 조성한다.

라이브 채팅 특성상 **초당 수십~수백 건의 메시지가 실시간으로 검사**되어야 하므로, 검사 지연시간(Latency)이 1ms 이하이어야 하며, 공백·특수문자·초성 변형(`시.발`, `ㅅㅂ`, `18년` 등)을 효과적으로 방지해야 한다.

또한 배달의민족 기술블로그 사례와 같이, **정상 단어 내 금칙어가 포함되어 억울하게 차단되는 오탐(False Positive)** 문제(예: `고르곤졸라` 내 `졸라` 탐지)를 구조적으로 방지하는 화이트리스트/블랙리스트 이중 검증 구조를 설계한다.

차단 대상은 두 갈래다. **① 단어로 잡는 것** — 비속어·차별 표현·사칭 키워드 (2~4장), **② 모양으로 잡는 것** — 전화번호·계좌번호 (5장). 후자는 목록으로 관리할 수 없어 사전이 아닌 패턴으로 판정한다.

## 2. 기술 선정 및 이유 (Technical Rationale)

### 2.1 Aho-Corasick (아호코라식) 알고리즘 선택 이유

| 검사 방식 | 시간 복잡도 | 처리 속도 | 비고 |
|---|---|---|---|
| 단순 `String.contains()` 반복 | $O(N \times M)$ (N: 텍스트 길이, M: 금칙어 수) | ~10ms 이상 | 금칙어가 3,000개일 때 초당 1,000건 처리 불가능 |
| 정규식 (Regex Pattern) | $O(N \times M)$ 계열 | ~5ms | 규칙이 복잡해질수록 CPU 사용량 급증 |
| DB SQL (`LIKE '%욕설%'`) | Disk/Network I/O 수반 | 10~50ms | 동접 200명일 때 DB Connection Pool 고사 |
| **Aho-Corasick 트라이 자동화** | **$O(N + K)$** (K: 매칭 횟수) | **< 0.1ms** | **금칙어 수(3,000+)와 무관하게 문장 길이에만 비례** |

- **선정 이유**: Aho-Corasick 알고리즘은 3,000개가 넘는 금칙어 패턴을 단 1회의 트라이(Trie) 탐색으로 처리하므로, 실시간 라이브 채팅 환경에서 유일하게 $O(N)$ 성능을 보장하는 구조이다.

### 2.2 인메모리(Classpath Resource) 처리 이유

- **이유**: `src/main/resources/slang/*.txt` 파일(예: `리그오브레전드_필터링리스트_2020.txt`)을 앱 기동 시(`@PostConstruct`) 1회 로딩하여 메모리(RAM)상에 Aho-Corasick 자동화를 구축한다.
- **효과**: DB 조회 0회, Disk I/O 0회로 검사 속도 0.01ms 달성 및 메모리 점유율 2MB 이하 유지.

### 2.3 LLM (Gemini API 등) 미사용 이유

- 라이브 채팅 메시지 1건마다 외부 LLM API를 호출하면 200~500ms 네트워크 지연 및 API 과금/Rate Limit이 발생한다. 따라서 실시간 실효성이 떨어지므로, 인메모리 규칙 엔진을 주검사기로 사용한다.

## 3. 우아한형제들(배민) 모델 기반 이중 검증 구조

배달의민족 통합금칙어시스템의 화이트리스트/블랙리스트 메커니즘을 적용한다.

```
                  [ 입력 텍스트 (예: "고르곤졸라 맛있어") ]
                                    │
                                    ▼
                     [ 1단계: 정규화 (Normalization) ]
             공백 축약, 특수문자 제거, 소문자화 ("고르곤졸라맛있어")
                                    │
                                    ▼
                [ 2단계: Aho-Corasick 블랙리스트 매칭 ]
               탐지된 금칙어 후보: "졸라" (Start: 3, End: 4)
                                    │
                                    ▼
                 [ 3단계: 화이트리스트 (Whitelist) 예외 판정 ]
    "졸라"를 포함하는 구간 [3, 4]가 화이트리스트 단어 "고르곤졸라" [0, 4]에 포함되는가?
                                   │
                   ┌───────────────┴───────────────┐
                   ▼                               ▼
               [YES (포함됨)]                  [NO (독립 쓰임)]
            ✅ 정상 메시지로 통과               ❌ 금칙어 차단 (예외 발생)
```

### 3.1 3단계 검증 프로세스

1. **정규화 (Normalization)**:
   - 특수문자/문장부호/공백 제거 (`씨.발` ➔ `씨발`, `ㅅ.ㅂ` ➔ `ㅅㅂ`)
   - 사칭 방지 키워드 및 대소문자 통일
2. **블랙리스트 (Blacklist) 탐지**:
   - `slang/*.txt`에서 구축된 Aho-Corasick 트라이를 통해 금칙어 후보 및 매칭 위치(`startIndex`, `endIndex`)를 빠르게 도출.
3. **화이트리스트 (Whitelist) 예외 필터링**:
   - 복합 명사이거나 허용 단어 사전(`고르곤졸라`, `시발점`, `시발역`, `조까치` 등)에 포함된 키워드인 경우, 금칙어 매칭 위치가 화이트리스트 범위에 완벽히 포섭되면 차단 대상에서 제외.

### 3.2 화이트리스트 운영 시 주의점 — 블랙리스트와 같은 단어를 넣지 말 것

**한 줄 요약: 화이트리스트에 블랙리스트와 똑같은 단어를 넣으면, 그 금칙어는 통째로 풀린다.**

화이트리스트는 "이 금칙어가 **더 긴 정상 단어 안에 들어 있을 때만** 봐준다"는 장치다. 그런데 화이트리스트 단어와 블랙리스트 단어가 **완전히 같으면** 매칭 구간까지 같아지므로, 포섭 판정(`black.start >= white.start && black.end <= white.end`)이 **항상 참**이 되어 그 단어는 어떤 문장에서도 걸리지 않는다.

> 비유하자면, "졸라"를 봐주는 조건이 "고르곤졸라라는 울타리 안에 있을 때"인데, 울타리를 단어 자신과 똑같은 크기로 쳐버린 셈이다. 울타리가 곧 그 단어이므로 언제나 울타리 안에 있게 된다.

실제 사례 — `whitelist.txt`에 `개새`가 있었고 블랙리스트(`리그오브레전드_필터링리스트_2020.txt:379`)에도 `개새`가 있어, `이 개새 뭐야` 같은 문장이 그대로 통과했다. (`개새끼`는 더 긴 매칭이라 정상 차단되어 겉보기에 문제가 드러나지 않았다.) 2026-07-31 화이트리스트에서 `개새`를 제거하고 회귀 테스트를 추가했다.

**운영 규칙**: 화이트리스트에는 **금칙어를 부분 문자열로 포함하는 더 긴 정상 단어만** 등록한다. 단어를 추가하기 전 블랙리스트에 같은 단어가 있는지 반드시 확인할 것.

## 5. 연락처(전화번호·계좌번호) 차단

**한 줄 요약: 전화번호와 계좌번호는 "단어"가 아니라 "숫자의 모양"으로 잡는다.**

채팅으로 계좌번호를 뿌리거나 전화번호를 남기는 광고·사기 유도를 막는다. 금칙어처럼 목록으로 관리할 수 없는 대상(번호는 무한히 많다)이므로, 사전 대신 **패턴(정규식)** 으로 판정한다. 진입점은 동일하게 `SlangFilterService.validateText()`이므로 닉네임과 메시지 양쪽에 자동 적용된다.

### 5.1 왜 어려운가 — 축구 채팅은 원래 숫자가 많다

이 필터의 난이도는 "번호를 잡는 것"이 아니라 **"평범한 축구 대화를 안 막는 것"** 에 있다. 채팅에는 스코어(`3-1`), 포메이션(`4-4-2`), 경기 일정(`2026-08-15 21:00`), 시즌 표기(`2025-2026`), 등번호 나열(`7, 9, 10, 11`)처럼 숫자와 하이픈이 상시 등장한다. "숫자 10자리 이상이면 차단" 같은 단순 규칙은 경기 일정 얘기를 통째로 막아버린다.

### 5.2 판정 규칙 (2단계)

| 단계 | 검사 대상 | 차단 조건 | 잡으려는 것 |
|---|---|---|---|
| **1차** | 원본 텍스트 그대로 | 구분자로 이어진 **숫자 묶음 3개 이내**이면서 숫자 합이 **10~16자리** | 일반적인 표기: `010-1234-5678`, `3333-01-1234567` |
| **2차** | 공백·특수문자를 모두 지운 텍스트 | 숫자 덩어리 **전체**가 휴대폰 번호 모양(`01[016789]` + 7~8자리) | 잘게 쪼갠 우회: `0 1 0 . 1 2 3 4 . 5 6 7 8` |

- 구분자로 인정하는 문자: 공백, `-`, `.`, `_`, `/`, `~`, `·`, `,`, `(`, `)`, `ㅡ` (최대 2글자 연속까지)
- 자릿수 범위 10~16은 **계좌번호(10~14자리)와 전화번호(10~11자리)를 함께 덮는** 값이다.

### 5.3 두 조건이 왜 저 모양인가 (오탐 방지 핵심)

**① 1차의 "숫자 묶음 3개 이내" 제한**

이 조건이 없으면 `2026-08-15 21:00`이 `2026`+`08`+`15`+`21` = 4묶음 10자리로 잡혀 **경기 일정 대화가 차단**된다. 3개로 제한하면 날짜(`2026-08-15`, 8자리)까지만 한 덩어리로 보고 통과시킨다. 실제 전화번호·계좌번호는 거의 예외 없이 3묶음 이하(`010-1234-5678`, `110-123-456789`)라 놓치지 않는다.

동시에 이 제한은 `등번호 7, 9, 10, 11, 14, 20, 21` 같은 나열도 막아준다 — 앞에서 3묶음씩만 끊어 보므로 합계가 10자리에 도달하지 않는다.

**② 2차의 "덩어리 전체가 일치" 요구**

부분 일치를 허용하면 오탐이 난다. 등번호 나열 `7, 9, 10, 11, 14, 20, 21`에서 공백·쉼표를 지우면 `791011142021`이 되는데, 이 안에는 `0111142021`(10자리, `011`로 시작)이라는 **휴대폰 번호처럼 보이는 조각**이 들어 있다. 그래서 숫자 덩어리의 일부가 아니라 **덩어리 전체**가 정확히 휴대폰 번호 모양일 때만 차단한다. `791011142021`은 12자리라 전체 일치에 실패해 통과한다.

### 5.4 동작 예시

| 차단 ❌ | 통과 ✅ |
|---|---|
| `010-1234-5678`, `01012345678` | `오늘 3-1로 이겼다` |
| `010 1234 5678`, `010.1234.5678` | `4-4-2 포메이션이 낫지 않나` |
| `02-1234-5678` | `다음 경기 2026-08-15 21:00 킥오프` |
| `3333-01-1234567` (카카오뱅크) | `2025-2026 시즌 기대된다` |
| `110-123-456789` (신한) | `등번호 7, 9, 10, 11, 14, 20, 21` |
| `1002 123 456789` (우리) | `전반 45분 후반 90분 총 135분` |
| `0 1 0 . 1 2 3 4 . 5 6 7 8` | |

위 표의 모든 항목은 `SlangFilterServiceTest`에 테스트로 고정되어 있다. 규칙을 손볼 때 오탐이 되살아나면 테스트가 먼저 깨진다.

### 5.5 알려진 한계 (의도적 미대응)

| 우회 방법 | 대응 여부 | 이유 |
|---|---|---|
| 한글 숫자 (`공일공 일이삼사`) | ❌ 미대응 | `일`·`이`·`삼`을 숫자로 치환하면 `이 경기 정말...` 같은 평범한 문장이 전부 깨진다. 얻는 것보다 잃는 것이 크다 |
| 영문 O를 0 대신 (`O1O-1234-5678`) | ❌ 미대응 | 숫자 옆 `O/o/l/I` 치환으로 대응 가능하나 오탐 위험이 있어 보류. 실제 악용이 관측되면 추가 검토 |

두 경우 모두 **읽는 사람은 알아볼 수 있으므로 완전한 차단은 아니다.** 이 필터의 목적은 무작위 광고 도배를 걸러내는 것이지, 작정한 개인을 100% 막는 것이 아니다 — 그 수준이 필요해지면 신고 기능과 IP 차단(`chat:banned`, `docs/redis-design.md` 6.8)으로 대응한다.

## 6. 예외 처리 및 정책

검사 진입점은 `SlangFilterService.validateText(text, fieldName)` 하나이며, 위반 종류에 따라 **다른 안내 문구**로 `ChatException`을 던진다. 사용자가 무엇을 고쳐야 하는지 알 수 있어야 하기 때문이다.

| 위반 종류 | 안내 문구 |
|---|---|
| 금칙어·사칭 키워드 | `사용할 수 없는 부적절한 표현이나 사칭 키워드가 포함되어 있습니다 ({항목}).` |
| 전화번호·계좌번호 | `전화번호나 계좌번호로 보이는 숫자는 입력할 수 없습니다 ({항목}).` |

`{항목}`에는 `닉네임` 또는 `메시지`가 들어간다.

- **닉네임 검증**: 사전 선점 REST API (`POST /api/chat/{matchId}/nickname`)와 채팅 전송 시점 양쪽에서 검사 ➔ REST는 HTTP `409 Conflict`, STOMP는 에러 프레임으로 회신.
- **채팅 메시지 검증**: `ChatService.send()` 내부에서 검사 ➔ 개인 에러 채널(`/user/queue/errors`)로 **보낸 사람에게만** 회신 (방 전체에 노출되지 않음).

## 8. 향후 확장성

- 서버 재시작 없이 운영 중 금칙어/화이트리스트 동적 추가가 필요할 경우, 관리자 API(`ChatAdminController`)를 통해 메모리 Aho-Corasick 트리를 즉시 재Reload할 수 있는 `reload()` 메서드를 제공한다.
- 연락처 차단은 현재 "숫자 모양"만 본다. 실제 운영에서 `계좌`, `입금`, `송금`, 은행명 + 짧은 숫자 조합 같은 문맥형 광고가 관측되면, 키워드 동반 조건을 추가해 자릿수 기준을 낮추는 방식으로 확장할 수 있다 (자릿수만 낮추면 오탐이 급증하므로 반드시 키워드와 함께 판정할 것).
