# 8/15 매치 채팅방 실사용 기록

대상: **8/15 00:30 마르세유 vs AT 마드리드**. 휴대폰으로 접속, 중계는 쿠팡플레이.
설계 문서: [live-match-feed-design.md](live-match-feed-design.md)

---

## 증상

| # | 증상 |
|---|---|
| ① | 킥오프 직후 시계가 쿠팡플레이보다 **90~95초 빨랐다.** 첫 골이 나온 뒤 맞춰졌다 |
| ② | 골 효과 직전에 친 채팅이 **효과가 끝난 뒤에** 올라왔다 |
| ③ | 하프타임인데 **시계가 안 멈추고 계속 셌다** |

---

## ①③의 원인 — 스코어보드를 갱신할 통로가 골 알림뿐이었다

화면은 `live.periods.firstHalfStarted`(실제로 공이 굴러간 시각, FotMob 제공)가 있으면 그걸로,
없으면 `live.kickoff`(**예정** 시각)로 시계를 센다.

서버는 `periods`를 제때 받아 Redis에 저장하고 있었다. **문제는 프론트로 내보내는 통로였다.**

```
pollMatch()
  ├─ writeState(...)          ← Redis에는 매 턴 저장된다
  └─ publishGoalChanges(...)  ← 브로드캐스트는 골·VAR 취소 때만
```

- **①** 입장 시 `periods`가 없어 화면이 예정 킥오프로 셌다. 실제 킥오프가 그만큼 늦어서 그만큼
  앞서 간 것이다. "첫 골 뒤 맞춰졌다"는 것도 같은 이야기 — **골 메시지가 기준점을 나르는 유일한
  수단**이었다
- **③** 하프타임엔 골이 없다 → 브로드캐스트가 한 번도 안 일어남 → 서버는 `firstHalfEnded`를
  받아 놓고도 말을 안 한 상태

프론트의 시계 계산은 처음부터 하프타임을 올바르게 처리하고 있었다. **프론트는 잘못이 없었다.**

### 고친 것

**㉠ `STATUS` 메시지 타입 신설** — 골 없이 상태만 바뀌는 순간(킥오프·하프타임·후반 시작·종료)에
`live` 스냅샷만 발행한다. 본문이 비어 있어 채팅 라인으로 안 그려지고, `chat:msg`에 저장하지도
않는다(대화가 아니므로). 발행 조건은 `status` 또는 `periods` 변화뿐 — 점수는 골 알림이 이미 나른다.

> 프론트는 손댈 게 없었다. 봇 필터가 `!m.type || m.type === 'USER'`이고 `setLive`가 그 앞에서
> 돌기 때문에, 새 타입은 자동으로 "채팅 라인엔 안 뜨고 스코어보드만 갱신"이 된다.

**㉡ FotMob 시계 조회 간격을 구간별로** — 60초 고정이던 것을, 시계가 실제로 틀어져 있는
구간(기준점 미확보·하프타임·전반 43분 이후)만 15초로. 전반 한복판은 60초 유지.

**㉢ 상태가 바뀐 턴에는 간격을 무시하고 즉시 조회** — 네이버가 5초마다 보고 있어 하프타임을 가장
먼저 안다. ㉡만으로는 리허설에서 하프타임이 다 지난 뒤 `firstHalfEnded`가 도착했다.

**㉣ Jackson 왕복 버그** — `previous.periods != state.periods`로 비교했는데 `previous`는 Redis에서
읽어 온 값이라 Jackson이 오프셋을 UTC로 옮긴다. `+09:00`과 `Z`는 같은 순간이어도 `equals`가
거짓이라, 그대로 뒀으면 **조용한 45분 내내 5초마다 도배**됐을 것이다. `Instant` 비교로 수정.

## ②의 원인 — PC와 모바일의 GPU 성능 차이

조명 셰이더(`stadiumLightsGL.ts`)가 **픽셀마다 조명 5개를 루프**로 돈다. 조명 하나당 `exp` 2회 +
`pow` 2회 + `atan` + `sin` 2회 + `smoothstep` + `length` — 픽셀당 약 50번의 초월함수 연산이다.

폰 화면 430×932에 해상도 상한 1.5배면 90만 픽셀. **프레임당 4,500만 연산**, 60fps면 초당 27억이고
여기에 LED 보드 셰이더가 또 얹힌다. 데스크톱 GPU에는 껌이지만 폰 GPU는 여기서 무너진다.

**GPU가 프레임을 제때 못 그리면 같은 프레임에 실려 있던 채팅 메시지도 같이 늦게 칠해진다.**
DOM은 100ms 만에 바뀌어도 그 프레임이 화면에 나오는 건 GPU가 풀린 뒤다. 그리고 이 셰이더는
**연출이 없으면 아예 안 돈다** — 골 순간에만 부하가 계단식으로 뛰는 구조라, "연출 중에만,
끝나면 바로 정상"이라는 증상과 정확히 맞는다.

데스크톱에서는 같은 조건에서도 증상이 안 났다. 연출 5.2초 내내 60fps, 롱태스크 0건, 연출 시작
4ms 뒤 보낸 메시지가 30ms 만에 DOM에 삽입됐다. 백엔드·프론트 로직·스크롤 모두 이상 없었다.
**PC와 폰의 차이 하나만 남는다.**

### 고친 것 — 모바일에서만 조명 연출을 가볍게

| 조치 | 효과 |
|---|---|
| 모바일에서 조명 캔버스 해상도 상한 `1.5` → `0.75` | **픽셀 수 1/4** (실측 749,280 → 187,600) |
| 셰이더 루프의 `pow(x, 2.0)` → `x*x` (전 기기) | 초월함수 2개가 곱셈 1개로 |

```ts
const cap = isMobileDevice() ? LIGHTS_MAX_DPR_MOBILE : LIGHTS_MAX_DPR_DESKTOP;
const dpr = Math.min(window.devicePixelRatio || 1, cap);
```

**모바일 판정은 화면 너비로 하지 않는다.** 데스크톱 창을 좁게 줄인 것과 진짜 폰이 구분되지 않는데,
가리고 싶은 건 화면 크기가 아니라 GPU다. `(pointer: coarse) and (hover: none)` — 마우스가 없고
포인터가 뭉툭한 기기가 실제 모바일에 가장 가깝게 맞는다.

해상도를 낮춰도 눈에 안 보인다. 원래 뿌옇게 번지는 빛이고, 코드 주석도 "해상도를 다 쓸 이유가
없다"고 적고 있었다. 데스크톱 화질은 그대로다.

부족하면 다음 단계가 있다: 모바일에서 조명 5개 → 3개(40% 절감), 그래도 안 되면 조명 레이어만
드롭(흔들림·섬광·진동·LED 보드는 남는다).

## 검증

리허설(`scripts/fake-live-match.js`) 2회 — 골 15/15, VAR 취소 3/3, `STATUS` 정확히 4건.

```
킥오프    10:05:13 → STATUS 10:05:16
하프타임  10:08:28 → STATUS 10:08:31   firstHalfEnded 정확
후반 시작 10:08:43 → STATUS 10:08:46
경기 종료 10:10:13 → STATUS 10:10:16
```

전환마다 3초, 조용한 구간 중복 발행 없음. 테스트 11건 추가, 전체 통과.

②는 폰 실기기 확인을 못 했다 — 폰에서 3000은 열렸지만 Windows 방화벽이 java.exe(8080) 인바운드를
막았고, 회사 PC라 규칙을 추가하지 않았다. **8/20 말라가전이 첫 실사용 확인이다.**

## 8/20 말라가전 결과 → [round1.md](round1.md)

여기서 고친 ①③이 **실경기에서는 통하지 않았다.** 네이버의 하프타임 표기가 `전반종료`인데
종료 판정의 `contains("종료")`가 이걸 경기 종료로 읽어, 폴러가 전반 끝나자마자 멈췄기
때문이다. 골 알림까지 통째로 죽었다. 경위와 후속 수정은 [round1.md](round1.md)에 있다.

이 문서에서 "리허설은 통과했지만 실경기는 처음"이라고 적어둔 것이 그대로 터진 셈이다.
리허설이 하프타임 표기로 **지어낸 값**(`하프타임`)을 쓰고 있었던 것이 직접 원인이다.

②(골 연출 중 채팅 지연)는 8/20에도 확인하지 못했다 — 그 전에 골 알림 자체가 안 나갔다.
